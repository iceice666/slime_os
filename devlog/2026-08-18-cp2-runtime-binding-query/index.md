## Summary

Adds `CAPABILITY RESOLVE BINDING` (label 37): a component asks the root which of
its own CSpace slots holds a named generation binding, instead of compiling the
number in from a `build.rs`-private constant table. The root answers from the
calling instance's *own* binding list, scoped by the badge it authenticated, with
the name bounded and UTF-8-validated before any table walk. A name the instance
does not bind is refused, never answered with another instance's slot.

`console` and `init` are migrated and their planes pass: `init`'s
`console_send_slot()` previously chose between two compiled constants on the
authenticated boot action, and now asks by name; `console`'s
`SHARED_BUFFER_FACTORY_SLOT = 1` is now a query.

CP2's full exit condition — all 19 `include!` sites — is **not** met, and the
reason is a real blocker rather than remaining effort. The query answers manifest
grant bindings, which is what an instance's binding list holds. `init`'s 61 slots
are not that: they come from `contracts/boot-layout/v1`'s resource object, which
is one table describing the bootstrap component's CSpace (`path=init`), keyed by
role and identity hash rather than by instance. A fallback to that table was
written and proved unsound on a real boot. Making those slots resolvable needs a
boot-layout format change, which is not a root change.

## Decisions

- **Decision:** the query answers only from the calling instance's own binding list; the boot-layout fallback was removed.
  **Rationale:** the fallback was written, built, and booted. `contracts/boot-layout/v1`'s resource object is one table for the bootstrap component's CSpace and declares every plane's edges — `console-output` and `dango-output` both — so answering from it returned slots for names the caller had never bound. That is exactly the leak this operation must not have, and it surfaced as a *hang* rather than a wrong number: under the product graph `init` asked for the edge it binds, received the layout's other edge, and sent into an endpoint nobody was waiting on. The fallback and its helper are gone.
  **Rejected alternative:** keeping it restricted to the bootstrap instance. That would still answer names `init` had not bound, because the leak is the table's shape rather than who reads it.

- **Decision:** the operation is gated by no right.
  **Rationale:** it discloses which of the caller's own slots holds a binding the caller's own instance declares — a fact the component previously had compiled into its image. Requiring a right would mean minting a capability whose only power is reading one's own layout. Recorded in `docs/capability-matrix.md` beside the rights table rather than left as an omission.

- **Decision:** `console`'s self-check asserts the denial arm only, not a resolved slot number.
  **Rationale:** two earlier versions asserted more and each was wrong. Asserting `slot == 0` failed under the product graph, where the same edge lands elsewhere. Enumerating `console-output`/`dango-output` failed under the dango plane, which names it `dango-console-rpc`. Both put a manifest fact back into a component's source — the coupling being removed. The grant arm is proved where the name is a legitimate local fact: `console`'s own factory grant and `init`'s own channel edge, both on real boots, where a wrong answer is a failed rendezvous rather than a passing test.

- **Decision:** `init`'s `console_send_slot()` tries three names.
  **Rationale:** the three current generations spell one edge three ways and no generation binds more than one, so this is a disjoint lookup rather than a precedence rule. A list of names is still a manifest fact in that source, and a smaller one than the slot numbers it replaces: the numbers differed per generation and had to be selected by boot action, while a name is stable across every generation declaring that edge. Collapsing the three spellings is a fixture change that would delete the list.

- **Decision:** CP2 is recorded as mechanism-complete with a partial migration rather than as complete.
  **Rationale:** 2 of 19 sites are migrated. The other 17 are not remaining effort — they are blocked on `contracts/boot-layout/v1` gaining a per-entry owning instance, plus the separate fact that 46 of `fabric_profile`'s 64 constants are graph facts (route tables, QoS depths, trace depth) rather than slots, for which a slot query is the wrong instrument. Claiming CP2 complete would misreport that.

## Open risks and follow-ups

- [ ] 17 `include!` sites remain. The unblocking change is a `contracts/boot-layout/v1` format revision recording which instance each entry belongs to; `init`'s 61 slots then become resolvable by the existing query.
- [ ] `fabric_profile`'s non-slot constants need their own answer. A slot query cannot serve a route table or a QoS depth; those are graph facts a component could read from the authenticated `fabric-graph` resource object instead.
- [ ] The three-name list in `init`'s `console_send_slot()` is a residual manifest fact. Giving the edge one name across the fixtures deletes it.
- [ ] Ordered name probing in `init`'s `console_send_slot()` depends on no generation binding two of the names to one instance. That holds for every current fixture and nothing enforces it; the enforcement belongs in `build-generation.py` rather than in a component.
- [ ] Every failed resolution writes a serial line, and the operation is ungated by design, so a probe loop degrades the root's dispatch latency. The channel gate asserts the exact line, so rate-limiting rather than deleting it is the fix.
- [ ] `B70` stays open. Its first two clauses are closed by CP0/CP1 and its third is now partially closed: the query exists and is used, but component sources still `include!` `build.rs`-private tables.

## Corrections

**2026-08-18 — the "blocked" claim in *Summary*, *Decisions*, and *Open risks*
was wrong.** This entry's frozen body records that serving boot-layout slots
"needs a boot-layout format change, which is not a root change", and lists the 17
remaining `include!` sites as blocked on it. That is not true, and the body is
left as written because the reasoning that produced it is the useful part.

What was actually wrong: the fallback had no namespace. Two revisions were tried
and both failed on real boots — first serving the layout to any caller, then
restricting it to the bootstrap instance. Both failed for the same reason, which
is not instance scoping at all: the layout and the grant list use overlapping
names for *different things*. `console` is a layout executable at slot 1 while
`init-console` is a grant at that same slot; `console-output` is a grant under the
product graph and absent from the channel plane's layout. A flat lookup therefore
answered a channel question with an executable slot, and `init` sent into an
endpoint nobody was waiting on — a hang rather than a visible error, twice.

The fix needed no contract change. The caller now states which table it means:
`executable:` and `channel:` address the two identity domains
`contracts/boot-layout/v1` already declares to keep a component and a channel
sharing a name distinct. An unprefixed name is a grant and can never reach the
layout, so no layout entry can shadow a grant. `init` resolves four layout-only
executable slots at runtime across the channel and dango planes.

Verified: `just runtime_binding_resolution_check`, `just test`,
`just sel4_channel_check`, `just sel4_dango_check`, `just sel4_loan_check`,
`just sel4_boot_check`, `just sel4_spawn_check`, `just sel4_component_graph_check`,
`just fmt_check_all`, `just lint_all`. `test_sel4_root` is 124/124 — the new
`layout_namespaces_are_distinct_domains` test asserts the two domains differ,
which is the property the prefix relies on.

Still remaining, and genuinely not blocked: the `fabric_profile` sites. 46 of
their 64 constants are graph facts rather than slots, so a slot-resolution query
is the wrong instrument; those components should read the authenticated
`fabric-graph` resource object instead.
