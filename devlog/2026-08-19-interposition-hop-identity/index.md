# Interposition hop identity moves from broker constants to root admission

| Field | Value |
|---|---|
| Date | 2026-08-19 |
| Kind | Defect |
| Status | Verified |
| Scope | `slime-root/src/{generation,main}.rs`, `components/bins/src/{matrix,visibility}_broker.rs`, `components/bins/src/default_fabric_profile.rs`, `scripts/build/build-generation.py`, `scripts/check/check-sel4-{matrix,visibility}-plane.py`, `scripts/check/check-sel4-gate-controls.py`, `Justfile` |
| Roadmap | B70 |
| Gates | `just sel4_matrix_check`, `just sel4_visibility_check`, `just sel4_gate_control_check`, `just sel4_fabric_aggregate_check`, `just generation_check`, `just contracts_check`, `just test_sel4_root` |
| Trigger | B70 migration of `FABRIC_INTERPOSITIONS` off the build-time manifest tables |
| Baseline | Both plane gates green; `assert_declared_chain` present in both brokers |

## Summary

Both fabric brokers asserted their declared interposition chain by comparing a
build-time constant table (`FABRIC_INTERPOSITIONS`) against a proxy name
compiled in beside it (`const PROXY: &[u8] = b"fabric-proxy"`). Both operands
were generated from the same manifest into the same crate, so the check could
only ever confirm the table agreed with itself. Substituting a different
declared component onto the chain in the fixture produced a generation that
admitted cleanly and a matrix gate that stayed **green** — the plane gate could
not tell which component the generation had put on the chain. The hop name is a
generation fact, so it is now resolved and emitted by the root that admits the
generation, and asserted by the plane gates instead. Both `assert_declared_chain`
bodies are deleted, satisfying B70's exit clause for this table. The same
perturbation that previously passed now fails.

## Observable symptom

- Command: `just sel4_matrix_check`, with `sel4-matrix.zti`'s chain changed from `"fabric-proxy"` to `"fabric-probe"`
- Expected: the gate refuses a generation whose declared chain names a different proxy
- Observed: exit code 0, `seL4 matrix plane check: ... the declared proxy was the only telemetry path`
- Exit/fault/serial evidence: the perturbed boot admitted with `interpositions=1` and every existing marker satisfied; `assert_declared_chain` did not fire, because the build-time table regenerated to match the perturbed fixture

## Investigation log

| Step | Observation | Consequence |
|---|---|---|
| 1 | `assert_declared_chain` compares `FABRIC_INTERPOSITIONS` (generated by `components/bins/build.rs` from the manifest) against `PROXY`/`DOWNSTREAM` constants in the same crate | Both operands move together when the fixture changes; the check is self-referential |
| 2 | Enumerated `component = "..."` inside `sel4-matrix.zti`'s `fabricGraph` block: seven participants, `fabric-proxy` absent | The hop is not a graph participant at all |
| 3 | `slime-root/src/ipc.rs:755` sets `GRAPH_ROW_BYTES = PARTICIPANT_ENTRY_BYTES`, and `read_graph_participants` iterates `0..graph.participant_count()` | Op 38 pages participant rows only; no re-scoping of it can ever surface a hop identity |
| 4 | `grep -n interposition slime-root/src/ipc.rs` is empty | No userspace-facing interposition mechanism exists |
| 5 | `build-generation.py:2163-2181` appends hops to a `hops` list separate from `participants`; the participant carries only an integer `interposition_head` index | The hop identity lives solely in the 40-byte interposition-entry section |
| 6 | `generation.rs:367-374` checks hop *membership* (`declares(hop.component_identity)`) and nothing about which hop was expected | `fabric-probe` for `fabric-proxy` is a valid graph, not an admission error — explaining the green perturbation run |
| 7 | `participants_are_declared` already reverse-maps identity to name by hashing each declared instance name with `fabric_graph::component_identity` | The root can name the hop with no new syscall and no schema change |

## Root cause

The chain's hop identity crossed a process boundary as a hash
(`InterpositionEntry::component_identity`) whose preimage exists only as an
instance name in the generation. Nothing in userspace could invert it, so the
brokers asserted against a build-time copy of the manifest instead of against
the graph the root actually admitted. The violated invariant is B70's: a
component's assertion about the generation must derive from the admitted
generation, not from a table compiled into the component making the assertion.
The absence of a hop-identity check in the plane gates was the secondary
symptom; `assert_declared_chain` was the innocent-looking site that appeared to
cover it.

Both perturbations were run against the migrated code and restored afterward
(`git diff --stat` on each fixture is empty). They are the load-bearing result:
they show gate power was strengthened rather than relocated, which re-running the
pristine gates alone could not show.

The visibility perturbation substitutes `fabric-publisher-b` — a component that
fixture *declares* — deliberately. An undeclared name would be refused by
`participants_are_declared` at admission, and the gate would then fail on the
admission error rather than on the missing marker, proving only that the
pre-existing membership check still works. Substituting a declared component
keeps admission succeeding (the transcript ends `[init] visibility plane
complete` with every task exiting 0), so the only thing that can fail is the new
marker, and that is exactly what fails.

## Decisions

- Decision: resolve the hop name in the root and assert it in the plane gates, rather than adding a graph-interposition syscall.
- Rationale: the root already holds both operands — it decodes the graph and reads the instance names — and already performs this exact reverse map for hop membership. A syscall would add ABI surface, a `contracts/syscall-abi/v1/schema.zt` change, and a new authority-scoping question, to move a fact that only a gate needs to observe.
- Decision: delete `FABRIC_INTERPOSITIONS` outright once the assertion was gone, rather than leave it generated-but-unread.
- Rationale: B70's exit clause is about what a component `include!`s, and an unread table still ships in every profile and still invites the next self-referential check. The precedent is `FABRIC_SUPERVISION`/`FABRIC_SUBSCRIBERS`, deleted the same way for the same reason. `just generation_check` proves the emission's removal is byte-safe.
- Rejected alternative: a new holder-scoped operation over `InterpositionEntry`. Correct but disproportionate: no component needs the hop name at runtime; only the gates assert on it. Also rejected: widening `fabric_self_view::Row` or re-scoping op 38 — impossible, since a hop holds no participant row (investigation steps 2–3).

## Open risks and follow-ups

- [ ] Remaining B70 tables are unmigrated: `FABRIC_CLIENTS`, `FABRIC_PARTICIPANTS`, `FABRIC_QOS`, `FABRIC_HISTORY_DEPTHS`, `FABRIC_VISIBILITY`, `FABRIC_NOTIFICATION_BINDINGS`, `FABRIC_MINTED_GRANTS`, and `GENERATION_BOOT_ACTION` (bootstrap-only, and an authority question rather than a mechanical migration). Per-symbol use counts recorded in earlier notes were not reproduced this session and should be recounted with the next migration rather than carried forward.
- [ ] The checked-in `default_fabric_profile.rs` named `fabric-service` as the interposition hop where every real fixture names `fabric-proxy` or `fabric-intruder`, and nothing caught it. Worth asking whether the other checked-in default rows are equally unchecked against the fixtures they stand in for.
- [ ] The gates pin the hop name as a literal. A fixture legitimately renaming its proxy must update the gate — deliberate, matching how the other `SLIME_ROOT` counts are pinned.
- [ ] B72 and B73 remain open and are adjacent to this area.
