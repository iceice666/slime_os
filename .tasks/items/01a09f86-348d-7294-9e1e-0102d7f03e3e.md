# Extract current architecture from chronological records

## Problem

Current architecture, plans, decisions, delivered chronology, and historical
evidence are mixed in `roadmap/` and `devlog/`. Readers must reconstruct how a
live subsystem works by following milestone order and dated records, and some
roadmap pages compete with code and contracts as a current specification.

## Scope

- Begin with `roadmap/02-core-runtime.md`. Extract current IPC, fabric,
  scheduling/time/lifecycle, task-private memory, and other actual subsystem
  documentation according to the content found; do not preserve C7/C8/C9/C10
  delivery order as the information architecture.
- Verify every statement about current behavior against the owning source,
  Zutai schema, generated/validated binding, fixture, or live gate. A conflict
  is resolved from current owners or documented precisely; documentation work
  must not modify runtime merely to make prose true.
- Classify `roadmap/README.md` and every remaining roadmap file individually:
  current ownership/boundaries/invariants to `docs/architecture/` or an existing
  good owning page; unimplemented design and qualification requirements to
  `docs/plans/`; exploratory directions remain in `docs/directions/`; delivered
  chronology and old gate narratives remain historical.
- Distill only still-valid material from
  `devlog/2026-08-24-mcs-cost-reassessed/`,
  `devlog/2026-09-13-mem-64m-private-reuse-cycles/`, and
  `devlog/2026-07-24-boot-check-hangs/`. Preserve proposal status, separate a
  reusable verification method from one run's result, and move only current
  troubleshooting conclusions from the old boot investigation.
- Add `docs/decisions/` and `docs/plans/` only when populated with substantive
  content. Keep existing sound documents in place rather than moving them to
  satisfy a directory diagram.
- Update README/docs navigation, agent routing, and live work-item design
  references so current, planned, exploratory, and historical material have one
  clear owner. Do not create a second state table.
- Retain source roadmap/devlog text until H3 has verified its archive.

## Exit conditions

1. A reader can understand each extracted core-runtime subsystem without
   traversing chronological devlogs or milestone delivery order.
2. Current behavior, accepted/proposed decisions, unfinished plans,
   exploratory directions, and historical narrative are visibly distinct.
3. Every current technical claim is traceable to owning implementation,
   contract, fixture, observation record, or current gate.
4. Proposed decisions remain proposed unless separately accepted through the
   repository's decision process.
5. README, docs navigation, agent routing, and necessary active work-item links
   resolve to one current owner; unextracted roadmap pages are clearly retained
   rather than silently duplicated.
6. Product source, generated output, ABI, pins, image identity, and every MyQue
   item state/relationship are byte-for-byte unchanged.
7. Existing historical files remain available for the H3 anchor and all active
   local links/fragments/UUIDs pass.

## Non-goals

Do not mechanically rename `roadmap/`, rewrite every historical statement,
complete unimplemented plans, change a subsystem to fit documentation, alter
task state, or delete/archive source records in this stage.

## Verification

Run the current documentation/link checks, `just tasks_check`, `just typos`,
and `just devlog_check` while the legacy corpus remains. Run source-backed
inspection or a narrow gate only where a current claim cannot otherwise be
established; documentation-only edits do not manufacture runtime evidence.
