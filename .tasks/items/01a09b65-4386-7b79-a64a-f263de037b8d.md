# Device-derived private-memory capacity and demand-backed use of spare RAM

## Context

The requested outcome is to use a device's available ordinary RAM automatically,
not to replace a 64 MiB constant with a 1 GiB constant. Under unchanged explicit
workload policy, a larger kernel-visible RAM inventory must allow a larger private
working set, and an idle holder's elastic maximum must not reserve the entire pool.
Available means ordinary RAM handed to root by seL4 after exclusions, less measured
system commitments and declared reserves; it never means installed RAM or MMIO.

This is an independent continuation related to the existing capacity epic, not a
sixth child silently added to its frozen five-child qualification scope. The
completed segmented-backing and ordinary-inventory work are dependencies. MEM-1G
remains a separate, open fixed-workload qualification: its evidence must be
preserved or rerun if shared mechanisms change, but completing a fixed 1 GiB
workload is not a technical prerequisite to researching adaptive capacity.

Research and design rationale: [device-derived memory capacity](../../devlog/2026-09-13-mem-adaptive-device-capacity/index.md).

## Observed starting point

- `contracts/private-memory-budget/v1/schema.zt:37-57` sets target-qualified
  compile-time ceilings; the current QEMU rows are 64 MiB per holder / 128 MiB
  aggregate. Board defaults remain 2 MiB / 8 MiB. These are policy/qualification
  ceilings, not measurements of device RAM.
- `slime-root/src/task.rs:739-780` and
  `slime-root/src/object_allocator.rs:610-699,2118-2154` reserve an entire task quota
  in physical extents, CSlots and descriptors before publishing the task. Mapping
  is lazy, reservation is not. A nonzero one-page quota reserves a whole 2 MiB
  data extent and a 4 KiB table extent.
- The private total tracks committed pages, not all reserved backing. Freeing a
  heap allocation only recycles it inside the live component; task teardown owns
  system-level reclamation. Runtime growth already returns explicit failure and
  preserves existing bytes on refusal.
- BootInfo ordinary ranges and actual root CSpace availability already exist.
  Root nevertheless has a 524288-slot software bitmap limit, packed slot fields,
  fixed descriptor pools and compile-time per-region leaf bitmaps. The host
  backing planner also stops at 256 MiB per holder. These are implementation
  barriers, not acceptable replacement product ceilings.
- Inherited inventory evidence is 1584454000 ordinary bytes on ARM and 3195192256
  on RV64. Calculated payload-only 4 KiB frame counts are 386829 and 780076;
  RV64 alone exceeds the current 524288 root slots before non-data costs. A
  large-frame-only estimate cannot promise arbitrary small-page growth.
- `scripts/build/build-sel4.py:657-698` bakes the pinned memory size into the
  kernel DTB. Adaptive root allocation cannot discover physical RAM omitted by
  that description. A launcher-only RAM increase proves nothing.

## Scope

### Device-derived capacity and accountable resource pools

- Derive effective capacity from actual BootInfo ordinary ranges and reusable
  backing, with checked arithmetic and exact extent/alignment fit. Account for
  boot exclusions only once: memory already absent from BootInfo is not deducted
  again. Separately charge root metadata, kernel objects allocated by root,
  staged/static tasks, page tables, shared-buffer/DMA commitments, and an explicit
  operational/restart reserve. Do not consume device-untyped regions.
- Size or grow bounded CSpace/descriptor/span tracking from admitted resources,
  with a small bootstrap path. Resolve packed-field, extent-index and root-image
  feedback constraints. Do not compile maximum-device-sized arrays into every
  board image or merely widen the old target page constants. Bootstrapping the
  metadata must itself fit and be included in the resource ledger.
- Report ordinary inventory, excluded/committed system costs, guaranteed backing,
  elastic reserved extents, committed payload, metadata/slots, reusable capacity,
  policy limits and the actual limiting resource separately. Residual unusable
  RAM must have an observed reason, not be hidden behind a fixed GiB ceiling.

### Explicit adaptive authorization, not implicit authority

- Define adaptive private-memory policy in a versioned Zutai contract and generate
  every persisted/IPC binding. Separate holder opt-in, guaranteed capacity,
  maximum authorized growth and the device-derived shared elastic pool. Permit
  an explicit pool-relative authorization so a normal capacity increase requires
  no pageQuota or per-target private-capacity table edit.
- The admitted generation carries deterministic policy, not a host machine's
  resolved free-RAM number. Resolve device-dependent capacity from the trusted
  boot inventory; identical policy and inventory produce identical admission
  results. Policy is declared by the composition/userspace owner; root implements
  accounting, validation and allocation, not application importance heuristics.
- An omitted holder has no private-memory authority even when RAM is idle.
  Guarantee, authorization maximum and current availability are distinct. All
  guaranteed commitments must be simultaneously affordable; elastic maxima are
  permission to request, never promises that all maxima can be satisfied together.
  Successful growth must always obtain real backing before success is returned.
- Specify contention ordering and instance/subtree accounting. Repeated spawn of
  one component cannot multiply its declared guaranteed entitlement or evade a
  shared policy budget. Preserve explicit fixed-budget semantics through an
  intentional version/migration decision; never reinterpret an old quota as
  best-effort elastic capacity silently. Migrate affected callers/fixtures/docs
  in one coherent cutover, with no competing hand-written format or alias path.

### Demand-backed elastic growth and lifecycle

- Reserve a stable guarded virtual window at task construction, independently of
  physical commitment. Native pointers and the base remain stable for the task
  lifetime. Check address ceiling, large-frame alignment, upper/leaf table costs
  and collisions with every other mapping path for device-derived window sizes.
- Reserve guaranteed resources before publication. Obtain elastic backing,
  descriptors and slots from a common reclaimable pool as growth requires them,
  rather than sequestering every holder's authorized maximum at spawn. Preflight
  and commit the complete resource tuple transactionally. Refusal leaves prior
  mappings, contents and guarantees usable.
- Preserve exact page accounting with mixed 4 KiB/2 MiB mappings. Small-page and
  fragmented paths must use available resources safely, not rely on successful
  huge mappings or silently promise unrepresentable fallback capacity.
- Roll back newly acquired elastic resources on failed growth/construction where
  safe; any required retained table/extent remains explicitly charged and reusable,
  not invisible leakage. Release backing/charges only after successful revocation;
  failed teardown keeps ownership until retry. Task death returns capacity for
  other holders. No automatic stealing or shrinking of live private bytes.

### Platform and validation integration

- Reconcile host component-spec/system-spec/generation validation with runtime
  resolution, including malformed/unsupported policy versions and overflow cases.
  Keep policy identity distinct from the identity-bound boot platform inventory.
- Qualify multiple RAM configurations per QEMU architecture. Use unchanged root
  and component binaries plus unchanged adaptive policy when the kernel ABI is
  unchanged; platform kernel/loader/DTB artifacts may differ where upstream seL4
  requires it, and every run must name the actual identity. Do not claim a single
  self-discovering boot image if RAM topology is still compiled into the kernel.
- Record physical-board admission/boot constraints separately. The mechanism must
  not hardcode QEMU target-name capacity rows as its source of available RAM, but
  QEMU evidence alone cannot qualify a board or all installed hardware memory.

## Exit conditions

- On both QEMU architectures, run the same adaptive policy and root/component
  binaries against at least three qualified ordinary-memory inventories, including
  a constrained case and a case with more than 1 GiB of usable private payload.
  With no private page-limit edits, observed resident capacity increases with
  resources. Touch and recheck every committed page; sequential allocation totals
  and admission-only reports do not count as residency evidence.
- For an uncapped, explicitly authorized bulk holder, consume the calculated
  elastic pool up to the exact next-request resource refusal. Reconcile remaining
  ordinary/reusable RAM to named reserves, metadata, physical fragmentation and
  granularity; a still-fitting next request must succeed. Repeat with multiple
  simultaneous holders and mixed small/large growth, not just an optimistic
  large-frame benchmark. Report small-page versus bulk capacity differences.
- Two elastic holders can spawn with maxima that each permit the common pool:
  the first remaining idle does not prevent the second from using spare RAM.
  Once backing is committed it cannot be stolen. A later growth request under
  pressure fails explicitly without corrupting either holder. Guaranteed holders
  and the declared operational reserve remain serviceable under that pressure.
- Denied holders, duplicate-instance entitlement evasion, over-guaranteed policy,
  malformed versions, arithmetic overflow, reserved-window collisions, MMIO
  inclusion and launcher-only memory changes fail the owning boundary. Identical
  policy/inventory and the same request schedule reproduce the same decisions.
- Force partial allocation/map/construction failures and near-limit
  CSlot/descriptor/extent conditions. Existing bytes and guarantees survive;
  retries do not double-charge. Refused allocation cannot report success without
  backing. No swap, demand-zero overcommit or best-case-only guarantees.
- While peers retain patterns, fault and restart a holder for 20 coordinated
  cycles; returned capacity is usable by a different holder, new bytes are zero,
  and teardown returns reusable backing, slots, descriptors and quota totals to
  the pre-workload baseline without downward drift. Include a revoke-failure
  retry and shared-buffer operations within their unchanged declared budget.
- Existing fixed-budget private-memory behavior and any landed MEM-1G evidence
  remain valid under their own policy. Small-target bootstrap metadata fits the
  admitted profile or fails explicitly before publication; no physical capacity
  claim is made without a board-specific inventory and runtime observation.

## Non-goals

Swap, overcommit of guaranteed/committed backing, RAM hotplug, relocating native
heaps, automatic live shrink/decommit, compaction/page promotion, OOM killing,
new cores/threads, larger shared buffers or ELF limits, 1 GiB frame support, and
unqualified physical-board support are not implied. In-task `free` still does
not mean return-to-system; live decommit is a separate explicit contract decision.
Using spare RAM means serving authorized demand, not eagerly filling all RAM.
