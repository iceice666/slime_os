# QEMU TCP client byte stream over virtio-net: ARP, IPv4, ICMP echo reply, TCP open/send/recv/close to one declared destination

## Context

A new composition, `sel4-io-tcp`, binds `network-service` to `virtio-net-driver` over the
IO0 rings and loans the IO3 probe already uses, and runs smoltcp inside the service: ARP,
IPv4, ICMP echo reply, and a TCP client to one exact generation-declared destination. The
service's own address and MAC are generation data (`contracts/network-interface/v1`), its
tick rate comes from the root's clock authority (`CLOCK_RATE_READ`), and client bytes travel
in an IO0 queue per client with the existing 56-byte request and 24-byte completion as
payloads. The QEMU peer is a frame-level Python responder on the same UDP socket backend the
link plane uses, so every frame is observed and nothing depends on host networking.

No UDP, DNS, listen/accept, IPv6, or DHCP. Backend independence is not claimed: one backend
is exercised.

## Exit conditions

Under QEMU, `just io_tcp_check` observes: the service reports its declared interface and a
link that is up, answers the peer's ARP request and ICMP echo requests, opens a TCP
connection to the declared destination, sends 4096 bytes and receives them back byte for
byte, closes it, is refused by the peer on a second declared port, refuses an undeclared
destination before any frame leaves, and the plane ends healthy; `just io_link_check`
stays green; the intruder's refusals hold with zero frames at the peer.
