# Bounded capacity-scaled CSpace and reclaimable task backing

## Context

Large frames reduce object count, but the current per-task slot array and in-flight growth array scale with maximum 4 KiB pages. Each task also reserves one power-of-two untyped arena covering its image, kernel objects, and entire private quota. A large quota plus a small image can therefore reserve nearly twice the working set. Both costs must be bounded before publishing larger quotas.

## Scope

- Refactor the owning allocator, task construction/cleanup, private growth, and VSpace planning paths to account for frame extents and page-table objects rather than blindly multiplying global maximum pages by every possible task.
- Retain bounded ownership and full task-death revocation while allowing one task's backing to consist of multiple reclaimable untyped extents. Plan quota backing at admission/construction; on-demand frame mapping must not disguise an unreserved memory promise.
- Size actual root CSpace and software slot/descriptor bounds together. Any platform CNode adjustment includes its real RAM and boot-image cost, platform identity/pins, and the small-target configuration rather than an unconditional global increase.
- Account for adversarial legal growth sequences: many 4 KiB requests need more objects than one large request. Admission must reserve a defensible worst case, or a separately declared contract must state a resource bound; do not let a promised quota fail merely because a metadata table was undersized. No hidden rounding or uncharged preallocation.
- This milestone changes mechanism, not the public private-memory ceilings, shared-buffer ownership, or component ELF limits.

## Exit conditions

- Existing public-quota workloads boot on AArch64 and RV64 with segmented ownership. Host plans exercise 64 MiB and 256 MiB quotas without allocating a giant root stack scratch array or a maximum-page array for every task.
- Report root image/stack/heap metadata bytes, real free/required CSlots, page-table costs, alignment waste, and reserved versus mapped versus reusable RAM separately. Plans for four 256 MiB holders plus the root/product graph fit a 2 GiB physical envelope without four 512 MiB monolithic task reservations; this is a sizing result until the final live milestone.
- Full admitted quotas remain reachable for both bulk and one-page-at-a-time growth under the declared resource envelope. Explicitly test fragmented untypeds, descriptor exhaustion, slot exhaustion, and construction refusal before publishing a runnable task.
- Partial construction failure, repeated failed growth, normal exit, and fault cleanup return every extent and slot exactly once. A failed revoke remains owned and retryable; stale references cannot access a reused extent.
- Small-target builds retain their prior capacity envelope; no GiB-target metadata or CNode expansion is imposed on the Duo profile. Hardware runtime qualification remains a separate board claim.

## Reopened evidence

The 2026-09-11 per-region alignment simulation invalidated the original
four-holder sizing result: the AArch64 qualification reports
`ordinary_layout=0` and `fit=0` even though aggregate ordinary bytes are
sufficient. The exit condition requiring four 256 MiB holders to fit the 2 GiB
physical envelope is therefore unobserved, and this milestone is reopened.
The existing 512-page runtime, reclamation, bounded-traversal, and small-target
evidence remains valid. See the correction in
[the MEM-ARENAS devlog entry](../../devlog/2026-09-08-mem-arenas-segmented-backing/index.md#corrections).

## Observed closure evidence

The full reviewed verification campaign passed on 2026-09-12. Four 256 MiB
holder plans plus exemplar static backing require 1,077,936,128 bytes against
1,577,654,544 ordinary bytes remaining after staging the graph on the unchanged
2 GiB AArch64 QEMU profile; real per-region placement reports
`ordinary_layout=1 fit=1`. Required/available allocation descriptors are
263,520/264,268, extent descriptors 1,028/1,060, and CSlots 264,548/521,240.

Both QEMU architectures reached the unchanged public quota. AArch64 additionally
exercised failed-large-frame revocation followed by one-page and 511-page
growth, incremental rollback, and segmented task reclamation. Host tests passed
233/233, including repeated failed revoke ownership and a full one-page-at-a-time
retry. The actual Duo kernel/root/loader image built without expanded tables.
All gates named above passed, along with reclamation, contracts/generation,
closure/builder/run ownership, Python lint, development-log and work-item checks.

See [recycled-backing investigation and verification](../../devlog/2026-09-11-mem-arenas-recycled-backing/index.md).
The four large holders remain a sizing result, not live raised quotas or a
physical-board runtime claim.
