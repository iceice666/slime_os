# Adopt the published MyQue v2 envelope and Zutai-body devloop in Slime OS

## Problem

Developers need a repeatable path from structured requirements in a canonical
MyQue item to skill-driven implementation, review, verification, and
evidence-based completion. A separate live spec and a Markdown item describing
the same requirements introduce competing edit surfaces. Retaining every
completed item's full body indefinitely also grows the live work tree.

Keep MyQue as the work tracker. Evolve its supported format to `work-item/v2`
so that the frontmatter is an open record: MyQue owns a fixed set of envelope
keys and preserves every other key verbatim for consumers. MyQue does not
parse, frame, or validate the item body beyond the title; the body is opaque
Markdown to it. Slime OS then chooses, as its own body convention, that each
spec-driven item's body is exactly one fenced `zti` immediate-mode data block
carrying the requirements, validated by devloop's helpers rather than by MyQue.
Earlier specs were not retained; adoption must not reconstruct them or invent
provenance.

The work splits by ownership into two halves. The external half — MyQue's v2
envelope, retirement, migration, and `myque-gh` support, plus a standalone
devloop repository and release — is implemented and published, so this item now
covers the Slime OS half: the body convention, consumer policy, and integration
of the store's checks, docs, and projection consumers against those pinned
releases. Slime OS is an initial consumer, not a required execution environment
for either external project. Zutai does not replace MyQue's identity, state,
relationship, storage, or recovery responsibilities.

## Ownership split

| Concern | Owner | Location |
| --- | --- | --- |
| Versioned work-item envelope, fixed keys, open-record preservation rule, lifecycle, relationships, terminal records, migration | MyQue | MyQue project |
| GitHub projection and PR linking across v2, retirement, reopening | myque-gh | myque-gh project |
| Requirements-body schema, semantic helper primitives, evidence/execution contracts, skill, thin tool layer, body-profile validators | devloop | standalone `devloop` repository |
| Choice that the body is one fenced `zti` block, consumer gate policy, approval and commit rules, `just tasks_check` policy, docs, projection consumers | Slime OS | this repository |

Nothing below may be duplicated across owners. Slime OS must not carry a copy
of MyQue's envelope contract or devloop's schemas under its product tree; MyQue
must not learn devloop's schema; devloop must not embed a private work-item
parser or a second work-state store.

### MyQue: the envelope and machine API Slime OS consumes

- `myque api get UUID` returns one JSON object: `api` (`myque/v2`), `id`,
  `schema`, `state`, `title`, `body`, `bodyAvailable`, `consumers`, `revision`,
  `retired`, `ready`, `dependenciesDone`, and `history`. `body` is the opaque
  bytes after the title line, `consumers` maps a namespace to its complete raw
  YAML entry, and `revision` is the SHA-256 of the exact item bytes.
- `myque api create --admission TOKEN` reads `{title, kind, body, consumers}`
  on stdin and allocates the only UUID. Repeating a token returns the same
  identity; the same token with a changed payload is refused.
- `myque api put UUID --expected REVISION` reads optional `body` and
  `consumers` and patches only the namespaces it names, under a compare-and-swap
  on the exact bytes.
- `myque start UUID --expected REVISION` and `myque close UUID --expected
  REVISION` transition under the same lock that verified the revision, so a
  consumer eligibility decision cannot be overtaken by a competing write. A
  direct `myque close` without `--expected` still bypasses that boundary; this
  is MyQue's documented limit, not something Slime OS may claim away.
- Consumer-owned frontmatter is one lowercase `[a-z0-9_-]+` namespace per
  consumer. Slime OS uses `devloop` only; MyQue validates YAML syntax, rejects
  collisions with its own keys, accepts unknown namespaces, and never interprets
  them. Slime OS must not duplicate identity, title, state, timestamps, or
  relationships inside that record.
- Done and cancelled items retire to `.tasks/terminal/<UUID>.json`
  (`terminal-item/v1`) after their exact final bytes are retained in a verified
  Git commit reachable from `refs/myque/retained/*`. UUID resolution, parent and
  dependency edges, done-only readiness, and `myque check` then work offline
  from active plus terminal records, with `body: null` for retired items.
  Retained refs need an explicit refspec to travel between clones, and removing
  active files does not shrink Git history.
- Retention, reopening, and migration invoke Git, so the pinned executable must
  keep Git on its path; the published `myque-bin` output is wrapped with it.

### myque-gh: how the readable projection is wired

- `plan` and `apply` accept `--body-renderer EXECUTABLE` and repeatable
  `--body-renderer-arg ARG`. Slime OS configures exactly
  `--body-renderer devloop --body-renderer-arg render`.
- The renderer receives the supported `myque api get` JSON on stdin and returns
  Markdown on stdout. A renderer that fails, cannot start, returns invalid
  UTF-8, drops a nonempty description, emits reserved `myque:` markers, or hands
  back a structured fence is a local configuration failure before any GitHub
  discovery or mutation. There is no raw-body fallback.
- Without a configured renderer, a description that begins with a `zt` or `zti`
  fence is refused rather than projected. Legacy prose, including incidental
  code examples, is projected unchanged.
- Retired items keep resolving for relationships and pull-request links, and
  their descriptions state that the full body is unavailable offline. A retained
  commit is hyperlinked only when its recorded repository identity matches the
  store; otherwise the reference is plain text and the plan carries a
  `foreign-retained-history` warning.
- Neither an item body nor a consumer record can choose the executable or its
  arguments, and myque-gh never interprets consumer records.

### devloop: the contract Slime OS configures and calls

- Body profile `fenced-zti/v1`: the body after the title is exactly one fenced
  `zti` block holding a canonical `dev-spec/v1` payload, with no independently
  editable requirements prose beside it. A duplicate block, a missing block, an
  unrecorded or unknown profile, a tampered payload, and an unsupported API
  version are refused.
- The `devloop` frontmatter record is `devloop-consumer/v1`: body profile,
  requirements schema, helper identity, requirements digest, persisted admission
  identity, run epoch, and evidence entries. Evidence appends change only this
  record, so the requirements digest covers the stored payload alone.
- Installed contracts live under `$prefix/share/devloop/`:
  `contracts/dev-spec/v1/schema.zt`, `contracts/execution/v1/schema.zt`,
  `contracts/execution/v1/policy.zt`, `contracts/consumer/v1/schema.zt`, and
  `helpers/v1/validate.zt`. Each of those directories is its own Zutai package
  (`zutai.zti`) because the pinned compiler resolves a quoted import only
  downward from the importing file; the manifests are part of the helper
  identity, so Slime OS must not relocate or copy them.
- Consumer policy is `devloop-policy/v1` JSON: `schema`, `bodyProfile`,
  `codePaths`, `approvalArgv`, and `gates`. Each gate carries `id`, `mode`
  (`automated` or `human`), `argv`, `ttlSeconds`, and `observations` declaring
  `id` plus `kind` (`int`, `bool`, or `text`). Every observation a predicate
  reads must be declared, or the gate does not resolve.
- An automated gate receives `{item, acceptance, execution, inputs}` on stdin
  and prints a list of `{id, value: {kind, intValue, boolValue, textValue}}` on
  stdout; its real exit status is recorded. A human obligation is recorded only
  through `devloop human` with a real observation file and an observer.
- Commands select work by canonical UUID: `admit`, `validate`, `select`,
  `start`, `gate`, `human`, `eligible`, `complete`, and `render`, with
  `--policy`, `--inputs`, `--target`, `--image`, `--observations`, and
  `--observer`.
- Evidence binds the requirements digest, helper identity, code-path content
  identity, policy digest, execution-input digest, target, image, and run epoch.
  Changing any of them invalidates affected evidence, and the newest entry for
  an obligation decides it, so a later failing run is never satisfied by an
  earlier pass.
- Admission is the only evaluator use: a `.zt` authoring input is rendered once
  into canonical inert data with imported constants pinned, and a result that is
  not first-order data or whose imports do not resolve is refused. Validation,
  `just tasks_check`, and projection never evaluate `.zt`.
- Runtime prerequisites are the pinned `zutai-cli`, its standard-library root
  and native runtime archive, and `llc` plus `clang`, configured through
  `ZUTAI_STDLIB_ROOT`, `ZUTAI_RUNTIME_ARCHIVE`, `ZUTAI_LLC`, and `ZUTAI_CLANG`.
  The Rust admission bridge `devloop-zutai` is installed separately from the
  same revision. Each validation compiles and links a native binary, so it costs
  compiler startup, type checking, LLVM assembly, and process startup; there is
  no cached fast path to assume in Slime OS gates.

### What Slime OS must supply to these interfaces

- A `devloop-policy/v1` policy whose gate IDs resolve to existing `just`
  targets and `scripts/check/` mechanisms, with the typed observations each gate
  produces declared, and an `approvalArgv` that implements this repository's
  approval rules. Requirement text never carries shell.
- `codePaths` that name the code closure a gate actually tests, including the
  gate and approval programs themselves.
- A tracked `.tasks` tree, because retention and projection resolve terminal
  records and retained history from committed state.
- Pinned MyQue, myque-gh, and devloop versions in the dev shell, and the
  renderer flags above wherever projection runs.

## Inside Slime OS

### Body convention: the Zutai requirements block

Slime OS configures devloop with the `fenced-zti/v1` body profile. For every
item admitted to spec-driven execution, the body after the MyQue title is
exactly one fenced `zti` block holding a `dev-spec/v1` payload; the devloop
record in the frontmatter carries profile, pins, digest, admission identity,
and evidence. Legacy v1 and unmigrated plain-body items are unaffected and
remain ordinary work outside spec-driven execution.

This is a Slime OS choice, enforced by `just tasks_check` through devloop's
validator, not by `myque check`. Another consumer may choose a different
profile without any MyQue change.

#### Item shape under the published contract

The envelope below is `work-item/v2` as MyQue publishes it, and the body is the
canonical payload devloop's admission actually writes for `dev-spec/v1`.
MyQue owns every key above `devloop` and treats that record as opaque.

````markdown
---
schema: work-item/v2
id: <UUIDv7 allocated by MyQue>
kind: task
state: open
created: 2026-09-15T21:34:05+08:00
tags:
  - example
devloop:
  recordSchema: devloop-consumer/v1
  bodyProfile: fenced-zti/v1
  schema: dev-spec/v1
  helper: devloop-helpers/v1:<helper identity digest>
  requirementsDigest: <digest of the payload bound to schema and helpers>
  admission: <persisted admission identity>
  epoch: unstarted
  evidence: []
---

# Bound the request queue and explain overload

```zti
{
  schema = "dev-spec/v1";
  problem = "Overload must not exceed 64 queued requests or silently accept excess work.";
  scope = [
    "Bound queued requests and preserve FIFO.";
  ];
  nonGoals = [
    "Retries or durable storage.";
  ];
  requirements = [
    {
      id = "R1";
      statement = "Accept at most 64 queued requests and reject every excess request.";
      acceptance = [
        "A1";
      ];
    };
  ];
  acceptance = [
    {
      id = "A1";
      rationale = "Observe the actual queue at overload";
      gate = "queue-overload";
      mode = "automated";
      mandatory = true;
      predicate = "P1";
    };
  ];
  predicates = [
    {
      id = "P1";
      kind = "all";
      observation = "";
      expected = { kind = "bool"; intValue = 0; boolValue = false; textValue = ""; };
      lower = 0;
      upper = 0;
      lowerInclusive = true;
      upperInclusive = true;
      members = [
        "P2";
        "P3";
      ];
    };
  ];
}
```
````

Predicate variants are `kind`-discriminated records, not tagged unions: an
inert `.zti` payload has no representation for a tagged value, and it cannot
call a function. `P2` and `P3` are the omitted `bounds` and `equal` atoms that
`P1` composes. Slime OS policy resolves `queue-overload` to a real gate and
declares its typed observation outputs; the item supplies neither commands nor
its own notion of success.

An empty `devloop.evidence` list means no obligation is satisfied yet, not that
admission failed. Evidence appends change only the `devloop` record, so the
requirements digest is unchanged by them and a body edit invalidates it.
Completion consumes only the newest entry per obligation, bound to the exact
requirements, helpers, code, policy, execution inputs, target, image, and run
epoch that were tested.

#### Authoring input that computes the payload

The same requirements may be authored as a general-mode `.zt` input that
admission renders once. Reaching the published types needs a consumer-side
`zutai.zti` declaring the installed `contracts/dev-spec/v1` package, because
quoted imports resolve downward only. `limits.zti`:

```zti
{
  queueDepth = 64;
}
```

The authoring input:

```zt
limits ::= import "limits.zti";
s ::= import dev_spec.schema;
l ::= import stdlib.list;

ignored :: s.Value = { kind = "bool"; intValue = 0; boolValue = true; textValue = ""; };
noMembers :: List Text = l.empty ();

within :: Text -> Text -> Int -> s.Predicate
= id observation upper => { id =; kind = "bounds"; observation =; expected = ignored; lower = 0; upper =; lowerInclusive = true; upperInclusive = true; members = noMembers; };

{
  schema = "dev-spec/v1";
  problem = "The computed authoring path must pin shared constants at admission.";
  scope = { "Render a general-mode input to canonical inert data."; };
  nonGoals = { "Retaining the authoring input as a second spec."; };
  requirements = { { id = "R1"; statement = "The stored payload carries the pinned queue depth."; acceptance = { "A1"; }; }; };
  acceptance = { { id = "A1"; rationale = "Observe the rendered bound"; gate = "queue-overload"; mode = "automated"; mandatory = true; predicate = "P1"; }; };
  predicates = { within "P1" "peakPendingRequests" limits.queueDepth; };
}
```

Admission evaluates this once: `within` is applied and disappears,
`limits.queueDepth` is pinned as the literal `64`, general-mode `{ …; }` lists
become immediate `[ …; ]` arrays, and the formatted result becomes the stored
body. Editing `limits.zti` afterwards changes neither the stored body nor its
digest until someone re-renders and re-admits, which keeps evidence bound to
the requirements that were actually admitted. Neither the `.zt` source nor
`limits.zti` is retained as a second spec, and validation, `just tasks_check`,
and projection never evaluate `.zt`. A render whose result still contains a
function, or whose import does not resolve, is refused.

### Consumer policy and execution rules

- Apply Slime OS's planning, approval, backlog, verification, and commit rules
  through devloop's consumer-policy interface. Planning lands on `main` before
  a separate implementation PR; PR merge alone is not completion. Acceptance
  must not be weakened implicitly to obtain a passing run.
- Gate IDs resolve through Slime OS-controlled execution policy to existing
  `just` targets and `scripts/check/` mechanisms, never to arbitrary shell in
  requirement text. Declare each gate's typed observation outputs. This is not
  a security sandbox for an agent that already has shell access.
- Reuse or integrate the next-milestone implement/review/fix/verify sequence
  through the devloop skill, without Markdown checkbox selection or divergent
  execution rules. Work is selected by MyQue UUID.
- Physical-machine and human observations remain pending obligations until an
  operator supplies real evidence; nothing in Slime OS may synthesize them.

### Integration: checks, documentation, and projection consumers

- Extend `scripts/check/check-work-items.py` (`just tasks_check`), not a new
  checker: it already owns Slime OS policy over the store. Add the devloop body
  validation for items that carry a `devloop` record, keep delegating store
  validity to `myque check`, and keep backlog-first policy. Routine validation
  must stay offline.
- Update `scripts/lib/work_items.py` and every consumer that currently infers
  all identities from `.tasks/items/` filenames to resolve terminal records
  as well; cancelled, unknown, and corrupt identities are not done.
- Update `docs_check`'s canonical UUID resolution and the generated views
  (`tasks_list`, `tasks_next`, `tasks_graph`) for terminal records.
- Update `AGENTS.md`, `CONTRIBUTING.md`, and the decision record
  `docs/decisions/development-record-ownership.md` to route to MyQue's envelope
  and retirement contracts and devloop's requirements/evidence contracts, and
  to state the Slime OS body convention and gate policy. Do not copy either
  project's schemas under `contracts/`.
- Pin the compatible MyQue, myque-gh, and devloop versions in the dev shell.

## Exit conditions

### Published external prerequisites

Observed in the external projects and inherited here through the pinned
identities above, not re-proved by this item:

- MyQue `v0.2.0.0` publishes the open-record v2 envelope, the opaque body, the
  machine API, guarded transitions, migration, and the terminal-record
  lifecycle, with 135 behavior examples and its Nix package green.
- myque-gh `v0.2.0.0` projects v2 items through a configured body renderer and
  preserves identity, generated descriptions, pull-request links, and
  terminal-state behavior, with 68 behavior examples and its Nix package green.
- devloop `v0.1.0` is published with installable artifacts, its semantic
  helpers, body-profile validators, skill, and documentation; a clean
  installation outside this repository runs admit, start, gate, human evidence,
  completion, and render with no Slime OS paths.

A pin that is not yet published, or an external behavior this repository needs
but the release does not provide, is a real blocker for the conditions below.

### Inside Slime OS

1. Slime OS pins the published MyQue, myque-gh, and devloop releases and
   admits a real Slime OS item under the `fenced-zti/v1` convention; `just
   tasks_check` validates its body through devloop, still delegates store
   validity to `myque check`, still enforces backlog-first, and refuses the
   profile's negative cases. Legacy v1 items and plain-body v2 items still
   pass unchanged.
2. Slime OS gate policy resolves at least one automated gate to an existing
   `just` target with declared typed observations and one human gate to an
   operator observation; a passing run and a refused run are both recorded
   with their exact tested inputs.
3. Slime OS UUID resolution, `docs_check`, generated views, and projection
   consumers work offline against active and terminal records. Documentation
   and the ownership decision record route to the external contracts; no
   MyQue or devloop schema is copied under the product tree. Applicable
   Slime OS task and documentation checks pass. Record directly observed
   results and known limits before closing this item.

## Non-goals

Replacing MyQue or myque-gh; replacing MyQue's existing state meanings or graph
semantics; making MyQue parse, frame, or validate item bodies or consumer
frontmatter keys; keeping a separately editable spec store; inventing a general
workflow engine, new Zutai syntax, or compiler primitives; proving arbitrary
natural-language claims; automatic remote publishing or merging without
required authority; reconstructing unsaved historical specs; retaining complete
retired items in the live tree; rewriting Git history to reduce storage;
replacing current architecture or operating documentation with retired task
bodies.
