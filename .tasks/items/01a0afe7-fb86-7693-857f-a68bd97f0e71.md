# Bring up the Slime OS CPU and minimal component graph on Rubik Pi 3

## Problem

Slime OS has no declared Rubik Pi 3 / QCS6490 seL4 platform. The existing
AArch64 QEMU path does not establish the physical firmware handoff, interrupt
controller, serial console, timer routing, or safe memory map for this board.
The first delivery is a physical CPU boot and minimal userspace component
graph, not device support or a daily-driver operating system.

## Scope

- Identify the exact board revision and boot firmware, available exception
  level, secure/nonsecure handoff, PSCI interface, GIC layout, timer routing,
  UART registers and initialization, usable RAM and reserved regions.
- Establish a recoverable image-loading procedure. Prefer a transient or
  external-media path. Before any internal-storage or firmware write, identify
  affected partitions, preserve required original bytes, and establish the
  recovery tooling and operator steps. Do not infer recovery from an untested
  command or infer EL2 availability from an AArch64 Linux boot.
- Inspect the pinned seL4 and rust-sel4 sources, then implement the required
  board kernel/loader support with explicit pins and platform ownership.
- Add a distinct deterministic build target, admitted target profile and
  generated contracts, and a minimal generation with no unqualified device
  grants. Regenerate system-image closures with covered source changes.
- Qualify root entry, bounded allocation, physical timer delivery, endpoint
  IPC, component launch, fault isolation and cleanup on the named board.
- Extend the verification mechanism that owns physical boot evidence; do not
  add a top-level checker solely for a new board name. Bind observations to
  the exact board, firmware, source revisions and artifact hashes.

## Non-goals

USB, UFS, NVMe, Ethernet, Wi-Fi, Bluetooth, GPU/display, camera and accelerator
drivers; SMP qualification; DMA/IOMMU containment; production rollback; ROS 2;
and replacing Ubuntu as a supported daily-driver system. Debug UART output
alone is not completion of the minimal component-graph requirement.

## Implementation sequence

1. Land this work-item-only planning change on canonical main. Resolve,
   defer or block open backlog defects and establish the required green
   baseline before starting implementation.
2. Establish firmware, memory, console and recovery facts. If the current
   firmware cannot supply the existing EL2-based timer architecture, record
   the concrete blocker and review an explicit alternative before proceeding.
3. Bring up single-core kernel and loader output and root entry using the
   proven image-loading path.
4. Admit the board-specific target and generation, then qualify the minimal
   component graph and root mechanisms without peripheral authority.
5. Run regression checks, repeat physical boots, and document the reproducible
   build/load/recovery procedure and remaining unsupported boundaries.

## Exit conditions

- A clean checkout can resolve all pins and reproduce the board image with
  explicit target/configuration inputs; deterministic artifact checks pass.
- At least two physical cold boots of the same identified image reach root
  admission and the minimal component graph's ready marker. Record image
  hashes, board revision, firmware identity and operator-observed cold boots.
- Board-bound evidence demonstrates allocation, timer progress, IPC, child
  launch, fault isolation and reclamation, not merely a firmware banner.
- Missing, reordered, explicit-failure and wrong-image evidence are refused
  by the owning validator. QEMU evidence cannot satisfy the physical claim.
- The chosen recovery procedure is exercised, and retained original artifacts
  or a verified unchanged internal image are identified as appropriate to
  the loading method. Do not claim no internal writes when Ubuntu itself
  may have updated its filesystem during preparation.
- Narrow behavioral checks and applicable host, contract, generation, closure,
  formatting and lint gates pass. Existing supported targets do not regress.
- Current documentation describes the exact supported CPU boot boundary,
  commands, limitations and unqualified devices. Observed closure evidence
  is recorded before this item is marked done.

## Initial observation and limits

During the initiating session, the attached USB serial interface identified
itself as VID:PID `1a86:55d3`, serial `5A9B110113`. A ten-second read at
115200 8N1 included `Chip Name : QCS6490`, UFS boot, firmware
`6.0.250510.BOOT.MXF.1.0.c1-00312.1-KODIAKLA-3`, the device-tree model
`Thundercomm, Inc. RUBIK Pi 3`, and GNU GRUB 2.12 with Ubuntu entries.
This is a direct session observation, not retained image-bound qualification:
it proves neither Linux login nor Slime OS execution nor EL2 availability.
The board revision and boot image hashes were not collected. No board writes
or serial commands were issued for that observation.

The user selected CPU and minimal-component bring-up as the first stage and
authorized hardware operations. That authorization is not evidence that an
unknown flash command is correct or that the board is recoverable.
