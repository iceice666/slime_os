# Bring up the Slime OS CPU and minimal component graph on Rubik Pi 3

## Problem

Slime OS has no declared Rubik Pi 3 / QCS6490 seL4 platform. The existing
AArch64 QEMU path does not establish the physical firmware handoff, interrupt
controller, serial console, timer routing, or safe memory map for this board.
The first delivery is a physical CPU boot and minimal userspace component
graph, not device support or a daily-driver operating system.

## Scope

- Identify the exact board revision and boot firmware, available exception
  level, secure/nonsecure handoff, PSCI interface, GIC layout, timer routing,
  UART registers and initialization, usable RAM and reserved regions.
- Establish a recoverable image-loading procedure. Prefer a transient or
  external-media path. Before any internal-storage or firmware write, identify
  affected partitions, preserve required original bytes, and establish the
  recovery tooling and operator steps. Do not infer recovery from an untested
  command or infer EL2 availability from an AArch64 Linux boot.
- Inspect the pinned seL4 and rust-sel4 sources, then implement the required
  board kernel/loader support with explicit pins and platform ownership.
- Add a distinct deterministic build target, admitted target profile and
  generated contracts, and a minimal generation with no unqualified device
  grants. Regenerate system-image closures with covered source changes.
- Qualify root entry, bounded allocation, physical timer delivery, endpoint
  IPC, component launch, fault isolation and cleanup on the named board.
- Extend the verification mechanism that owns physical boot evidence; do not
  add a top-level checker solely for a new board name. Bind observations to
  the exact board, firmware, source revisions and artifact hashes.

## Non-goals

USB, UFS, NVMe, Ethernet, Wi-Fi, Bluetooth, GPU/display, camera and accelerator
drivers; SMP qualification; DMA/IOMMU containment; production rollback; ROS 2;
and replacing Ubuntu as a supported daily-driver system. Debug UART output
alone is not completion of the minimal component-graph requirement.

## Implementation sequence

1. Land this work-item-only planning change on canonical main. Resolve,
   defer or block open backlog defects and establish the required green
   baseline before starting implementation.
2. Establish firmware, memory, console and recovery facts. If the current
   firmware cannot supply the existing EL2-based timer architecture, record
   the concrete blocker and review an explicit alternative before proceeding.
3. Bring up single-core kernel and loader output and root entry using the
   proven image-loading path.
4. Admit the board-specific target and generation, then qualify the minimal
   component graph and root mechanisms without peripheral authority.
5. Run regression checks, repeat physical boots, and document the reproducible
   build/load/recovery procedure and remaining unsupported boundaries.

## Exit conditions

- A clean checkout can resolve all pins and reproduce the board image with
  explicit target/configuration inputs; deterministic artifact checks pass.
- At least two physical cold boots of the same identified image reach root
  admission and the minimal component graph's ready marker. Record image
  hashes, board revision, firmware identity and operator-observed cold boots.
- Board-bound evidence demonstrates allocation, timer progress, IPC, child
  launch, fault isolation and reclamation, not merely a firmware banner.
- Missing, reordered, explicit-failure and wrong-image evidence are refused
  by the owning validator. QEMU evidence cannot satisfy the physical claim.
- The chosen recovery procedure is exercised, and retained original artifacts
  or a verified unchanged internal image are identified as appropriate to
  the loading method. Do not claim no internal writes when Ubuntu itself
  may have updated its filesystem during preparation.
- Narrow behavioral checks and applicable host, contract, generation, closure,
  formatting and lint gates pass. Existing supported targets do not regress.
- Current documentation describes the exact supported CPU boot boundary,
  commands, limitations and unqualified devices. Observed closure evidence
  is recorded before this item is marked done.

## Initial observation and limits

During the initiating session, the attached USB serial interface identified
itself as VID:PID `1a86:55d3`, serial `5A9B110113`. A ten-second read at
115200 8N1 included `Chip Name : QCS6490`, UFS boot, firmware
`6.0.250510.BOOT.MXF.1.0.c1-00312.1-KODIAKLA-3`, the device-tree model
`Thundercomm, Inc. RUBIK Pi 3`, and GNU GRUB 2.12 with Ubuntu entries.
This is a direct session observation, not retained image-bound qualification:
it proves neither Linux login nor Slime OS execution nor EL2 availability.
The board revision and boot image hashes were not collected. No board writes
or serial commands were issued for that observation.

The user selected CPU and minimal-component bring-up as the first stage and
authorized hardware operations. That authorization is not evidence that an
unknown flash command is correct or that the board is recoverable.

## Recovery and EL2 handoff observations

Subsequent direct observations identified the PCB as V02 and retained verified
raw backups of every exposed UFS LUN before the firmware experiment. The
critical archive SHA-256 is
`ce9da3fe455fc0060a3b566c3da092f01fe333cf5d31f9205ef037f18093b2d2`;
separate resumable LUN images were compared against hashes computed on the
board. The official QLI 1.6 recovery XML set completed a QDL dry run, and an
EDL reset-only exercise uploaded its 1,024,000-byte Firehose programmer to the
observed device serial `8D194D08`, performed no partition program or erase,
and returned to the original Ubuntu installation. A later Firehose read-only
SHA-256 of both boards' active `xbl_config_a` region matched the retained bytes
at `4bb1729e5a0241219877dc2b07c06795a24047ff9a11fc796e1ba476fc182062`.
A minimal recovery package for only those two regions completed its own QDL dry
run. The board's B-slot firmware regions were observed to be zero-filled and
are not a rollback generation.

The original firmware route entered a transient UEFI diagnostic at EL1 and
Linux reported Gunyah. Following Qualcomm's documented order, the
`VendorDtbOverlays=el2kvm` EFI variable and the matching official QLI 1.6
`xbl_config_kvm.elf` were applied to only `xbl_config_a`; fastboot reported the
single-partition write successful. The resulting Ubuntu boot directly reported
`CPU: All CPU(s) started at EL2`, created `/dev/kvm`, and reported
`VHE mode initialized successfully`, without the former Gunyah marker.

A same-kernel arm64 kexec control boot again reached EL2. A 4,096-byte,
position-independent arm64 Image probe with SHA-256
`38573c001b07c88d4186447b6c0681ea636abb40b7897ec4eaaff8f12702bbdc`
was then loaded non-persistently with the running device tree. Its direct GENI
UART output was `SLIME_RUBIK_KEXEC_CURRENT_EL=2 FDT_PRESENT`; it invoked PSCI
system reset and the board returned to the KVM-enabled Ubuntu boot. This
establishes a recoverable EL2 loader-development path, not a Slime OS boot.

The first host-built Rubik Pi seL4 artifact uses the conservative qualified RAM
window `0xa0200000..0xb9700000`; lower observed ranges remain outside seL4. An
early 958,664-byte mechanical `hello` Image, SHA-256
`7ad85b4be03f09dbd2aa9f32bf967071ba86eb5980b64822f9ce9220de7e927e`,
was accepted by kexec-tools with the captured running DTB hash
`860fb07a907c6ca55efa476e9136d75e45b3f5d3ad4873d759b7d7808a5946b2`
and unloaded without execution. Ubuntu's boot identifier was unchanged across
the exercise, so nothing executed.

Independent review then found that candidate unsafe for execution: its header
incorrectly advertised relocation, its `--mem-min=0x9ae00000` did not pin the
fixed-link loader at `0xa0400000`, and `--mem-max=0xa04ea0c7` left no room for
the page-rounded Image, DTB, or purgatory segments. The hash and bounds above
are retained only as a rejected load-only observation and must not be executed.
The corrected artifact clears the relocation flag, requires legacy
`kexec_load`, pins both the header and relative branch at the fixed base, and
reserves a separate bounded post-Image window for temporary kexec segments.

The seL4 GENI driver was also corrected before that artifact was rebuilt. The
Linux 6.8 console aborts a main-sequencer command that never reports done; the
first implementation returned instead, which would leave the serial engine
active and silence every later character. The driver now aborts on either
timeout.

The resulting image is 958,664 bytes with SHA-256
`40bb0ca7fe30b1d1e0fc13949c41a5ed3e64844f33e3dfeca41002576308e4b6`,
built from payload ELF
`f8d5e50a50fd7db7594e7060029a28bd94de956f417727cb9a3156a209bf9e37`.
On the board, `kexec -d -c --type=Image --mem-min=0xa0400000
--mem-max=0xa07fffff` reported `kernel_segment: 00000000a0400000`,
`text_offset: 0`, and `image_size: 0xea0c8`, then placed its three segments at
`0xa0400000+0xeb000` (image), `0xa04eb000+0x48000` (device tree read from
`/sys/firmware/fdt`), and `0xa0533000+0x4000` (purgatory), all inside the
reserved window and ending at `0xa0537000`. The image was unloaded without
execution, with Ubuntu's boot identifier unchanged across it.
That boot again reported `CPU: All CPU(s) started at EL2` and
`kvm [1]: VHE mode initialized successfully`.

## First physical seL4 execution

With that loading path closed, the image was executed. seL4 booted on the
QCS6490 and a root task ran. The captured debug UART output was:

```
seL4 kernel loader | INFO   Starting loader
seL4 kernel loader | INFO   Entering kernel
Bootstrapping kernel
Available phys memory regions: 1
  [a0200000..b9700000)
Reserved virt address space regions: 3
  [80a0200000..80a0454000)
  [80b96e9000..80b96e954d)
  [80b96ea000..80b9700000)
Booting all finished, dropped to user space
Hello, World!
```

That is the mechanical rust-sel4 `hello` root task, not `slime-root`, so it
proves the kernel, the loader platform, the declared RAM window, and the GENI
debug UART on real hardware — and nothing about Slime OS. Evidence is
`evidence/rubikpi3-hello-first-boot.bin` in the recovery tree, captured from
image SHA-256
`810bc34785bbe665133af1507a0d1244e7bc7be28f73ffe879f399942bec3e46`.

Two platform facts were observed rather than assumed. First, the board issues a
PMIC `PSHOLD` warm reset a short time after Linux stops running: an earlier
attempt at the loader's `Debug` log level was cut off mid-transcript, while the
same build at `Info` completed the whole boot before the reset. Slow polled
GENI output, not a code fault, was the difference. Recovery is therefore
automatic — the board returns to Ubuntu by itself — but any milestone requiring
a resident system must first account for that reset source. Second, the seL4
kernel is built without `KernelAllowSMCCalls`, so a root task holds no SMC
capability and cannot invoke PSCI itself.

## Slime OS on the board

The `aarch64-sel4-rubikpi3` target profile was then added, the platform was
routed through `scripts/build/build-sel4.py`, and `slime-root` was built and
admitted for that profile carrying generation
`67614a40419acc0fa5de3ee425f98dfd02e7aa787153267ecd6fe5cf7704dc21`.
The packaged image is 6,880,408 bytes with SHA-256
`b646197122d92e2ecff6952d970bbd00c9dd68abaa3d685d4f95dfca5ccdca28`.

It booted and ran to completion on the board. The captured markers include the
allocator's inventory (`untypeds=37 bytes=397925904`), the timer
(`SLIME_TIMER acquired irq=30 freq_hz=19200000`, then delivered, serviced, and
`advanced start=44823404561 end=44823692338 delta=287777`), request/reply IPC
against a spawned child, shared-buffer rights enforcement
(`ro_write=refused wx_execute=refused`), a private-memory quota refusal
(`QuotaExceeded { pages: 4, delta: 1, quota: 4 }`), a deliberate
`VirtualMemory { access: Write }` child fault observed and settled by the root,
full reclamation (`cleanup tasks=2 slots=108 live=0`), and the terminal
`SLIME_ROOT READY tasks=2 grants=2 declared_grants=11 reclaimed_slots=108`.
The seL4 `CNode Copy/Mint/Move/Mutate` kernel messages in that transcript are
the root's own negative controls, not failures. Evidence is
`evidence/rubikpi3-slime-root-first-boot.bin`.

That is a CPU and root-mechanism boot on one named machine. It is not device
support and not a repeatable gate.

## The reset bound, and what it blocks

The product component graph was then built for this profile
(`1d6ba8a512d044e81e76766cf7134f6bc763b0e41b264f6d87f852504ed31953`) and run.
It staged the graph, created its peer endpoints, and spawned `console`,
`spawn-service`, and `slisp` before the board reset mid-line. No component
reported ready. Evidence is
`evidence/rubikpi3-component-graph-truncated.bin`; the payload emitted 87,119
bytes, about 7.6 seconds at this console's 115200 baud.

A first reading treated those 87,119 bytes as a 7.6-second wall-clock budget
and inferred a platform timeout. That inference was wrong, and a direct
measurement replaced it. A bare arm64 payload carrying no seL4 at all -- a
probe that prints one line per second and re-reads the watchdog -- ran
continuously for 1,475 seconds without any reset, with the APSS watchdog enable
register reading zero throughout. Transcript length is not elapsed time on a
polled 115200 console, and no platform timer resets an EL2 payload here.

So the reset is raised by this software, not imposed on it. The board's APSS
watchdog is not the source either: `watchdog@17c10000`
(`qcom,apss-wdt-sc7280`) is `okay` in the device tree, but no Linux driver
binds it, `/sys/class/watchdog` is empty, and its enable register reads zero
both under Linux and under the bare payload. No PSCI `SYSTEM_RESET` or
`SYSTEM_OFF` call exists anywhere in the loader, the kernel port, or
`slime-root`.

`wfi` was the first hypothesis, because it is something every resetting run
reaches -- `hello` suspends its root thread, the root-boot fixture idles after
`READY`, and the graph's participants block on IPC, so seL4's idle thread
executes `wfi` -- and something the surviving bare probe never does. A second
probe that ticks five times and then enters a bare `wfi` loop refuted it: the
board sat in that loop silently and did not reset. Idle entry is not the
trigger.

Memory was the next hypothesis and it is also refuted. A probe that wrote and
read back one word per 4 KiB page across the entire declared window, loaded
below that window so it could not overwrite itself, walked all 407 MiB with no
mismatch, printed its completion, and reset the board through PSCI.

The framing itself was then corrected by timing the runs rather than reading
transcripts. Instrumented captures record when each marker arrives: seL4 enters
the kernel, drops to user space 40 ms later, reports the timer about a second
in, and reaches `READY` roughly seven seconds after entry. One instrumented run
reset somewhere between 140 and 170 seconds after entry. The next, from the
same image and the same command, ran past 366 seconds and then past fourteen
minutes, idle and silent, without resetting.

The retry settled it, and "intermittent" was also wrong. Two component-graph
runs, from different builds and different image sizes, stopped after the same
line -- `spawn authorized … component=slisp`, its schedule line, and the
backing allocation that follows -- and the second reset 10.0 seconds after
kernel entry. A `sel4-sample` run, whose composition contains no `slisp` at
all, reset 10.1 seconds after kernel entry at the analogous point, just after
spawning a component and allocating its backing.

So the trigger is neither one component nor chance. What separates the runs is
whether the system is still working when the tenth second arrives: the
root-boot fixture finishes at about seven seconds, suspends, and then idles for
quarter of an hour untouched, while both spawn workloads are still running at
ten seconds and are reset there.

Four explanations have been tested and refuted by measurement rather than
argument. A platform watchdog: a bare payload ran 1,475 seconds and the APSS
enable register reads zero throughout. Idle entry: a probe sat in a bare `wfi`
loop without resetting. Memory access: a probe wrote and read back every 4 KiB
page of the declared window with no mismatch. The console: a bare payload
emitted 9,040 lines over sixty continuous seconds, about 600 KiB, and then
reset itself on schedule.

The timestamps place the clock precisely. Measured from kernel entry, the two
resets fall at 10.13 and 10.15 seconds -- within twenty milliseconds of each
other. Measured from the first component spawn they fall at 5.83 and 3.44
seconds, nearly a factor of two apart. The deadline is therefore anchored at
kernel entry, not at anything the workload does.

That leaves a deadline armed when seL4 starts, which fires at about ten
seconds, and which an idle system survives while a working one does not. Both
halves of that are needed to fit the evidence, and one bare-metal observation
still sits awkwardly against it: a bare payload spinning in a tight loop with
the MMU off ran twenty-five minutes without resetting. What the bare probes
never do, and seL4 always does, is run with stage-1 translation and caches
enabled, program the interrupt controller, and take periodic timer interrupts.

The next experiment follows from that: a progression of bare-metal probes that
add one of those in turn -- MMU and caches, then the GIC, then a periodic timer
interrupt -- each staying busy past fifteen seconds and each resetting itself
through PSCI on a deadline. Whichever step first reproduces a reset at ten
seconds identifies the mechanism.

Diagnostic payloads should invoke PSCI `SYSTEM_RESET` on a deadline. The first
two looped forever and left the board needing a manual power cycle; the memory
probe did reset itself and recovered the board unattended.

Until that is understood, a Rubik Pi component-graph boot, a resident system,
and any repeated-cold-boot gate are blocked. No system-image closure names this
platform either: closures are keyed by a system spec, and no Rubik composition
has been declared.
