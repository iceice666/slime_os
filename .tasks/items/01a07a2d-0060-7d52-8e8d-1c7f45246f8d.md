# Target-qualified 64 MiB private component working sets

## Context

The first user-visible capacity target is a real 64 MiB private working set, not additional unused emulator RAM. Both QEMU architectures must carry this workload while small physical profiles retain conservative ceilings.

## Scope

- Make per-target private-region and aggregate capacity explicit in versioned Zutai-owned inputs. Update generators, component-spec quota validation in `scripts/lib/component_spec.py`, system-spec composition/admission, builder refusal, root admission, VSpace reservation/collision checks, component runtime private-heap batching, and `docs/capability-matrix.md` in one cutover. Target-neutral spec validation and target-qualified composition checks must agree without applying the QEMU ceiling to small targets.
- Set the initial QEMU qualification envelope to 64 MiB per holder and 128 MiB aggregate private working memory. Keep existing small-target limits unless separately qualified. Bind profile selection to the admitted target identity, not a caller argument or ambient environment.
- Distinguish virtual reservation, reserved physical backing, committed 4 KiB quota pages, frame-object count, and metadata overhead. Account for all resources before launch; no memory overcommit.
- Keep private memory non-transferable and non-executable. Shared buffers, ELF loading ceilings, swap, live shrink, page promotion, and hardware capacity claims are out of scope.
- Update the existing private-memory probe's fixed `MAX_PROBE_PAGES` runaway guard from the generated declared/profile bounds. Split bulk and incremental cases explicitly, including boundary and full-quota small-request evidence; size watchdogs from observed execution without removing fail-fast bounds. Carry these changes into the existing component-spec/system-spec negative fixtures.

## Exit conditions

- On AArch64 and RV64 QEMU, a declared component grows exactly 64 MiB through the public private-memory API, touching and verifying every page. A separate ordinary runtime-heap case holds 60 MiB of payload simultaneously within the 64 MiB quota; report payload, allocator overhead, and remaining capacity separately.
- A bulk exact-64-MiB private-growth case uses 32 large data frames; report extra small data frames and page tables separately for runtime-heap and incremental cases. A mixed sequence crosses 2 MiB boundaries without rounding the caller's quota or corrupting live bytes.
- Zero quota, per-holder over-declaration, aggregate over-declaration, wrong-target profile, unsupported contract version, and one-page-over-quota growth fail closed. Builder and root agree on the same declared budgets; insufficient physical backing or slots is refused before making a task runnable.
- The 128 MiB aggregate contract accepts two 64 MiB reservations where platform backing permits; existing small-profile admission still rejects a 64 MiB holder. Full concurrent 1 GiB qualification is not claimed here.
- Normal exit and deliberate task fault permit immediate reuse by a subsequent task; run 20 spawn/grow/exit or fault cycles with no downward drift in reusable memory, slots, or accounting and no stale data exposure.

## Verification

Gates to extend/run during implementation: `just contracts_check`, `just generation_check`, `just component_spec_check`, `just system_spec_check`, `just private_memory_check`, `just test_sel4_root`, `just test_host`, `just sel4_root_boot_check`, `just sel4_gate_control_check`, `just fmt_check_all`, `just lint_all`.

Use the existing private-memory probes and closure/spec pipeline, with the two-architecture execution support delivered by the prerequisite. Record exact image/profile identities and capacity evidence; compilation or a successful size query does not count as a working set.
