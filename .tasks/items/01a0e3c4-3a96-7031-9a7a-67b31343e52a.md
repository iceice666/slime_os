# Record the upstream seL4 AMD SVM and AMD-Vi gap and propose AMD IOMMU ownership

## Scope

X2 (`01a0724c-5400-75d8-b84d-a0695ac0e37a`) and H4 (`01a0724c-5400-70c8-9990-21edd1694e5f`) are written as if the kernel could host an AMD-V guest and contain DMA behind an AMD IOMMU on the Framework 13. Source reading of the pinned kernel (`deps/sel4`, fork commit `fea36b2`, 16.0.0) and of upstream `seL4/seL4` master (`0f10829`, 2026-09-22) shows neither exists: x86 virtualization is `KernelVTX` (Intel VMX/VMCS/EPT only), and `KernelIOMMU` is Intel VT-d only (`intel-vtd.c`, ACPI DMAR; no IVRS parser). Both options are also outside every verified configuration, and upstream `CAVEATS.md` states there is no interrupt remapping, so device passthrough to an untrusted guest is unsafe.

Deliver, as documentation only:

- X2 in `roadmap/05-foreign-workloads.md` and `docs/plans/existing-workload.md`: X2 requires an AMD SVM kernel extension and a Slime-written VMM before any guest runs, neither of which upstream provides;
- H4 in `roadmap/04-platform-hardware.md` and `docs/plans/framework-hardware.md`: the kernel has no AMD-Vi support, so containment ownership is an open decision rather than configuration;
- a `proposed` decision record in `docs/decisions/` choosing where AMD IOMMU programming lives (kernel IOSpace extension versus `slime-root`-owned MMIO programming), with alternatives, consequences, and revisit conditions, indexed from `docs/decisions/README.md`.

## Non-goals

- Any kernel, root, contract, or checker change; implementing SVM or AMD-Vi.
- Accepting the decision: it stays `proposed` until an implementation item owns it.
- Choosing guest GPU acceleration or the Radeon driver's scope.

## Exit condition

The roadmap and plan text above name the gap with the inspected kernel revisions; the decision record exists as `proposed` and is linked from `docs/decisions/README.md`; `just docs_check` and `just typos` pass; no runtime test is claimed. Record the observed run in the implementation PR.
