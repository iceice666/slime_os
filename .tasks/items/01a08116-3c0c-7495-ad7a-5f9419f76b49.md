# Private-growth rollback boundary, failed-map ownership, and worker IPC transparency

## Problem

Review of the private-growth capacity work found three correctness defects in
`slime-root`, each breaking an invariant the mechanism claims:

1. `unwind_private_transaction` revoked the parent untyped of any extent holding
   an in-flight allocation and cleared every allocation record in it. Private
   data extents are bump-allocated and are not isolated per growth transaction,
   so a failed second growth destroyed pages an earlier committed growth still
   owned while `region.pages` and the root-wide total stayed unchanged — a
   rollback that reported success and left the task's live memory unbacked.
2. `reset_private_in` marked a failed-map object `Empty` and reusable, and
   decremented live-object and live-byte counts, without deleting the capability
   or revoking the backing. The allocator then believed the CSlot was free to
   retype into while the kernel still held a capability there; the pinned seL4
   requires an empty destination slot, so the retry was refused rather than
   served. An empty region's first large-frame map failure produced no in-flight
   record at all, so the outer unwind could not recover the extent either.
3. `grow_private_memory` suspended and resumed sibling worker threads around the
   address-space transaction. In the pinned seL4, `suspend` begins with
   `cancelIPC` and `restart` sets `ThreadState_Restart`, so this is not a
   transparent pause: a worker with an outstanding `Call` had that call cancelled
   and restarted, which can re-execute a non-idempotent service side effect. A
   successful growth was sufficient to trigger it.

## Exit conditions

- A failed growth destroys only the objects that growth created; committed pages
  keep their backing and remain readable, with the sentinel written before the
  failure still intact afterwards.
- A failed mapping retains ownership of the retyped object as an unmapped,
  correctly typed reusable object, so the next growth of the same span succeeds
  with coherent capability, backing, and counts.
- Growing private memory does not alter any sibling thread's IPC state: a
  worker's delayed, side-effecting RPC executes exactly once and receives exactly
  one correct reply across a concurrent growth, and a growth request issued by
  the worker itself is adjudicated against the same task's region.
