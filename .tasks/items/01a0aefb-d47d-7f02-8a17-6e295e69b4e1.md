# Fault decoding reads stale fast registers after root receive

## Problem

The combined root service/fault receive path preserves received fast registers
only in the service request value, while fault decoding reads the IPC buffer.
Consequently the fault badge and label can be correct while instruction,
address, access kind and status are decoded from stale words.

This blocks accurate isolation/NX qualification for
`01a07a2d-00a1-727c-a548-130a4475f5bb`. It is not a request to relax fault
markers or to reinterpret a guard-write fault as execution evidence.

## Evidence and ownership

Source inspection at `90a184fb383ed9bfd800a243a32dd4e4ee06007b` establishes:

- `slime-root/src/ipc.rs::recv_request` and `recv_request_with` call
  `recv_with_mrs`, which returns the fast words in `RecvWithMRs.msg`.
- The pinned rust-sel4 implementation in
  `deps/rust-sel4/crates/sel4/sys/src/syscalls/calls.rs` routes
  `seL4_RecvWithMRs` through `seL4_RecvWithMRsWithoutIPCBuffer`. Unlike plain
  `seL4_Recv`, it does not copy the fast registers into the IPC buffer.
- `slime-root/src/graph_runtime/services.rs` calls `fault::decode_fault(&info)`
  on the fault-badge path. `slime-root/src/fault.rs::decode_fault` constructs
  `sel4::Fault` from the ambient IPC buffer, not the returned fast words.
- The service decoder's message-length bound cannot be used to discard or
  recover fault payloads: some fault messages exceed four words and still need
  the kernel-written tail.

During an uncommitted MEM-1G experiment, a deliberate guard store produced
`VirtualMemory { access: Execute, status: 0 } address=Some(9)`. This observation
motivated the source investigation; it is not a reliable access/address record
or a standalone reproduction at the base revision. Existing VM-fault occurrence
and task identity evidence must be distinguished from the untrusted details.
No corrected runtime fault attribution is claimed by this plan.

## Scope

- Restore the received valid fast words into the same IPC buffer used for
  reception before any buffer-based fault decoding, or use an equivalent
  receive/decode path with one authoritative payload source.
- Handle both ambient and explicit-buffer wrappers. Never update the ambient
  buffer when reception used an explicit one. Preserve kernel-written words
  beyond the fast-register prefix and do not overwrite words beyond the
  received length.
- Keep bounded service-request validation, badges, capability rejection and
  reply semantics unchanged. Timer notification wakes are not fault messages.
- Do not change upstream rust-sel4 to disguise the documented difference
  between its receive APIs. Do not introduce a second fault wire format.
- Audit buffer-based fault consumers and marker assumptions affected by the
  correction, without unrelated IPC refactoring or new top-level checkers.

## Exit conditions

- Host regression preloads stale words distinct from a received fault, then
  exercises the actual receive-boundary synchronization/decode helper and
  verifies fresh instruction/address/access/status values.
- Cover zero, short, four-word and longer receives; longer messages retain
  their tail. Explicit-buffer tests show the intended buffer changes and the
  unrelated ambient storage does not.
- Existing service-message length/capability refusals remain unchanged; a long
  fault must not be silently reduced to a rejected service request.
- On AArch64 and RV64, deliberate private guard stores report a Write VM fault
  for the correct task and the exact reserved-window end. A separate private
  execute attempt reports Execute at the backed private address. Do not count
  a guard/null fault as NX evidence.
- Wrong task, wrong access, wrong address, stale-register substitution and
  missing fault evidence are rejected by the owning tests/marker controls.
- Record target/profile, tested source and exact image identities, observed
  results and limits. A green unrelated gate does not establish fault payload
  correctness or close MEM-1G.
