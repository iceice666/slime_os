# Require a devloop spec-driven body for every new work item

This is an ordinary prose planning item, not an admitted devloop specification.
The policy it proposes takes effect on an announced date, not on this item's own
identity, so prose items created while it is in flight stay valid.

## Problem

Spec-driven bodies exist, are validated, and are optional. `just tasks_check`
decides which items are subject purely from the presence of a `devloop`
frontmatter record, and nothing requires a new item to carry one. The store
currently holds 310 items — 64 live, 246 retired — and **zero live items with a
devloop record**, so the
enforceable-completion path that `docs/decisions/spec-driven-work-item-bodies.md`
established is, in practice, unused. New work keeps closing on prose evidence a
reader interprets, which is the failure that record exists to prevent.

## Scope

1. **A cutoff rule in `scripts/check/check-work-items.py`.** An item whose
   canonical UUIDv7 timestamp is at or after `1790812800000` ms
   (`2026-10-01T00:00:00Z`) must carry a `devloop` consumer record.
   `just tasks_check` fails otherwise. The rule reads the identity alone, so it
   resolves offline and applies equally to live and retired items. Enforcement
   is hard: no exemption by `kind`, `tag`, or state.

   The date is announced rather than derived from this item so that work in
   flight between this plan and its implementation stays valid. No item in the
   store is at or after it; the newest identity, `01a0aefb`, precedes it by 13.5
   days. Enforcement must land before the date, or it will refuse prose items
   that were legitimate when written.
2. **A generic target gate in `.devloop/policy.json` and
   `scripts/check/devloop-gate.py`.** A gate identity that takes the `just`
   target name from devloop's execution `inputs` and reports one `passed`
   boolean from its exit status, so an acceptance can bind to any of the
   repository's 158 `_check` targets without hand-declaring typed observations
   for each. The existing `work-item-store` gate and its five typed observations
   stay as they are.
3. **Negative controls** proving the cutoff refuses a post-cutoff item lacking
   a record, accepts a pre-cutoff item lacking one, and that the generic gate
   reports a failing target as `passed: false` rather than as a gate that could
   not run.
4. **Documentation**: a decision record amending point 4 of
   `spec-driven-work-item-bodies.md`, plus the matching `AGENTS.md`,
   `CONTRIBUTING.md`, and `docs/getting-started/06-work-item-lifecycle.md`
   updates.

## Non-goals

- Retrofitting the existing live prose items, 65 once this one lands. The cutoff
  grandfathers them by identity, and reopening one never makes it subject.
- Declaring per-target typed observations for the 158 `_check` targets. The
  generic gate reduces a target to pass/fail; a check that deserves richer
  observations gets its own gate identity later, on demand.
- Closing the `myque close` bypass. That remains MyQue's documented limit.
- Any change to MyQue's or devloop's own schemas.

## Observable exit conditions

- `just tasks_check` fails, with an attributable message naming the item, when a
  post-cutoff item carries no `devloop` record; it passes when every post-cutoff
  item carries one.
- `just tasks_check` still passes with every pre-cutoff prose item untouched.
- A `just devloop gate` invocation resolving the generic target gate records
  evidence for a named `just` target, and records `passed: false` for a target
  that exits non-zero.
- The controls in scope item 3 run offline and are part of `just tasks_check`.
- `just ruff` and `just docs_check` pass.

## Known limits to record at closure

- A post-cutoff item can still be closed by a direct `myque close` without
  `--expected`, so a `done` state alone will still not prove devloop eligibility
  was checked.
- Moving the target name into operator-supplied `inputs` means the policy file
  no longer enumerates every command a gate may run. Requirement text still
  carries no command, which is the property the original record actually
  asserts.
