# An identity-bound 2 GiB AArch64 QEMU memory platform

## Context

The AArch64 product currently starts QEMU with 2048 MiB while `scripts/build/build-sel4.py` generates the pinned kernel DTB with 1024 MiB. Runtime `-m` is not evidence of kernel-visible RAM. Qualify a consistent 2 GiB platform independently of private-memory mechanism work.

## Scope

- Align the ARM kernel-build DTB, kernel physical-memory window, loader/platform prefix, closure/test-run parameters, pin/config hashes, and product invocation at 2048 MiB using the existing target-qualified build pipeline.
- Where memory-profile data crosses a build/boot boundary, use the existing versioned Zutai platform/closure contracts and generated bindings; do not add a hand-maintained parallel format.
- Inspect actual BootInfo ordinary-untyped ranges/counts, reserved ranges, free CSlots, and root/loader overhead. Device memory must remain outside ordinary allocatable RAM, and fixed untyped-descriptor bounds must cover the actual profile without silently dropping entries.
- Leave RV64's existing 3072 MiB QEMU profile and all physical-board memory maps unchanged. This milestone does not raise private quotas, add RAM hotplug, qualify 4 GiB/high physical addresses, or imply physical-machine support.
- Independence means no runtime-feature dependency, not concurrent mutation of a shared prefix or pin file. Build experiments use separate output prefixes; serialize integration of `sel4/pins.toml` and shared platform assets, then rebuild/revalidate the mechanism branch against the integrated identity. Either branch may land first without using stale artifacts as evidence.

## Exit conditions

- A fresh identity-bound 2048 MiB AArch64 build boots with both the kernel description and QEMU invocation naming that size. Two builds of the same inputs produce the same identity and required deterministic artifacts.
- BootInfo-derived ordinary allocatable ranges include usable memory beyond the old 1024 MiB platform window; report bytes/ranges after exclusions rather than calling all 2048 MiB free. A bounded root probe allocates an ordinary frame from that added range, maps it, writes/reads it, and releases it.
- A stale 1024 MiB prefix/DTB, a conflicting closure profile, and a launcher providing less RAM than the image requires fail the owning validation path before an unsupported run is reported successful. A negative control that changes only runtime `-m` cannot satisfy the kernel-memory evidence.
- Existing root boot, admission, fault, and cleanup evidence survives the platform rebuild. No hardware lane or private-memory ceiling is relabeled as qualified by this run.

## Verification

Gates to extend/run during implementation: `just sel4_pin_check`, `just sel4_root_boot_check`, `just sel4_boot_layout_check`, `just contracts_check`, `just generation_check`, `just sel4_gate_control_check`.

Extend the existing platform/root boot and closure validators rather than adding a standalone memory-size checker. Run `just ruff` for Python changes and `just fmt_check_all` / `just lint_all` for permanent Rust probe or mechanism changes. The direct added-range allocation is required even before the large-workload milestone.

## Observed closure

Closed on evidence, not on implementation status. Recorded in
[the ordinary-memory inventory entry](../../devlog/2026-09-13-mem-platform-ordinary-inventory/index.md).

- `just sel4_pin_check` passed with `qemu-arm-virt installed memory window verified`
  and `qemu-riscv-virt installed memory window verified`. The installed prefix's
  `platform_gen.yaml` window is now read and required to end at
  `dram_base + memory_mib`; the DTB RAM literal is gone and a one-sided edit was
  observed rejected, then reverted.
- `just sel4_root_boot_check` passed on `qemu-arm-virt` with
  `SLIME_ROOT ordinary ranges=34 bytes=1584454000 end=0xbf94c000`, an admitted range
  at `paddr=0x80000000 bytes=536870912` — exactly the retired platform's end — and
  `SLIME_ROOT ordinary probe paddr=0xbf948000 bytes=4096 beyond_legacy=1 verified=1`.
  Kernel-visible ordinary RAM therefore exceeds the old 1024 MiB window.
- RV64 passed independently: `ranges=40 bytes=3195192256 end=0x13f95a000`, probe
  `beyond_legacy=0` because that platform superseded no window. Its 3072 MiB profile
  is unchanged.
- `just sel4_gate_control_check` passed with 48 gates and 1937 mutated transcripts,
  including seven ordinary-inventory mutations: a runtime-`-m`-only change cannot
  satisfy the kernel-memory evidence, and a stale 1024 MiB window is rejected.
- `just sel4_boot_layout_check` passed: 31 plane layouts match their fixtures, so
  existing admission, fault, and cleanup evidence survived the change.

No private-memory ceiling and no hardware lane is relabeled as qualified by this run.
