# System image closures digest a submodule's .git gitlink, so every closure is stale in a git worktree

## Context

Observed 2026-09-11 in a fresh `git worktree` of `main` a1119ca6 with every submodule
initialised: `python3 scripts/generate/generate-system-image-closures.py --check` reports
all 50 closures stale, both through the serial path and the content cache, while every
zutai evaluation's stdout is byte-identical to the primary checkout's.

The cause is the kernel-loader implementation's identity: `identity_of` in
`scripts/generate/generate-system-image-closures.py` calls `tree_digest(deps/rust-sel4)`
with no `exclude`, so the submodule's `.git` gitlink file is part of the digest. Its
content is `gitdir: ../../.git/modules/deps/rust-sel4` in the primary checkout and
`gitdir: ../../../slime_os/.git/worktrees/<name>/modules/deps/rust-sel4` in a worktree.
Measured: the primary checkout's full digest `5dab11d1…` equals the committed identity,
the worktree's is `f316f538…`, and both are `d6ac5a3b…` with `.git` excluded. Every
closure names the loader, so every closure moves.

## Scope

- exclude repository metadata (`.git`, at least) from every tree input's digest in the
  generator and in `resolve_closure`'s recomputation, so a closure identity depends on the
  bytes a clone reproduces and not on how the checkout was made;
- regenerate the closures and blessed identities that carry the loader digest;
- add a control: a tree input whose only difference is a `.git` file resolves to the same
  identity.

## Exit conditions

`generate-system-image-closures.py --check` and `just system_image_closure_check` pass in a
`git worktree` with initialised submodules, and the primary checkout's identities are
unchanged by anything but the intended recomputation.

## Verification
