# Elastic rollback quarantine is never retried in production, its single slot can be overwritten, and one failure path does not quarantine the ledger member

## Context

Found by the 2026-09-24 post-closure stress audit of MEM-ADAPTIVE (source
reading; needs a kernel revoke failure).

`object_allocator/elastic.rs` stores a failed rollback in one
`elastic_quarantine` slot, which a second failure overwrites;
`retry_elastic_quarantine` is called only from
`private_memory/qualification.rs`. `settle_failure` quarantines the ledger
member forever (its `begin` returns `Cleanup` until retirement), while
`settle_refusal` and the lend-failure path do not quarantine the member at all.
`docs/architecture/private-memory.md` states that the next request is refused
and exactly one retry returns the resources; neither half holds in production.
Arena revocation still reclaims the backing at task death, so the effect is a
growth-dead incarnation and a stale slot rather than a lost range.

## Exit conditions

Every failed rollback is retained per arena and retried by production code, the
ledger member's quarantine matches the allocator's on every path, and the
documented behavior is what the code does.

Gates: `just test_sel4_root`, `just private_memory_adaptive_lifecycle_check`
