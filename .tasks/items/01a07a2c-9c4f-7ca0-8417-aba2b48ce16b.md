# Bounded memory capacity beyond the fixed private window

## Context

Plan the memory-only portion of the capacity direction as an independent continuation after the completed private-memory work, without reopening its historical parent. The user requested milestones for using more RAM; this plan names a qualification workload, not a new product/application claim.

## Scope

Five child milestones provide mixed-size frames, bounded scalable task backing, a 64 MiB working set, a kernel-visible 2 GiB ARM platform, and a simultaneous 1 GiB private workload. The platform branch is independent of the mechanism branch until final qualification. Canonical membership and dependencies are the UUID metadata, not roadmap headings or human keys.

No swap, overcommit, RAM hotplug, live shrink, automatic page promotion, new thread/core support, larger shared buffers, larger ELF images, or physical-machine support is included. This is a plan only: no runtime implementation or capacity evidence was produced during planning.

## Exit conditions

- Every child closes on its own observed exit conditions and links its implementation devlog.
- AArch64 QEMU on the qualified 2 GiB platform and RV64 QEMU on its existing 3 GiB platform each run four simultaneously resident 256 MiB private holders with isolation, exact budgets, failure recovery, and repeated fault/restart reclamation.
- Small-target capacity remains separately bounded and unclaimed without board-specific evidence. Document frame versus metadata costs and explicit resource refusal, not merely emulator RAM size.

## Verification

The children's named existing gates own runtime evidence. Before implementation, resolve/defer/block any open backlog and establish the required green baseline; a verification campaign is a precondition, not an extra milestone. The current state and readiness come only from MyQue.
