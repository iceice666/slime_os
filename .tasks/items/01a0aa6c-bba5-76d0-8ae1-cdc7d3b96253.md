# Automate retirement PRs for completed MyQue work items

## Problem

The pinned MyQue 0.2.0.0 supports explicit retirement but does not retire an
item when it closes. Future completed items therefore need a repeatable
maintenance workflow that preserves exact history and proposes a reviewable
storage transition without deciding whether the work was completed correctly.

Retirement is independent of envelope migration: ordinary work-item/v1 and
work-item/v2 items may both retire without changing their envelope version.
MyQue owns identity, storage transactions, retained snapshots, and recovery;
this repository owns candidate selection, evidence policy, and publication.

## Scope

- Add a separate `.github/workflows/myque-retire.yml`, scheduled daily and
  manually dispatchable. Manual dispatch defaults to preview, with an explicit
  option to publish a PR. Read only canonical `main` at a recorded full commit;
  do not accept arbitrary source refs or commands.
- Select only live items with state `done`; exclude cancelled, unfinished, and
  already retired items. An empty candidate set succeeds without publishing a
  branch or PR. Do not impose an additional age threshold.
- Use an isolated checkout, the pinned tools, complete repository history, and
  explicit fetches of `refs/myque/retained/*`. Serialize runs with a dedicated
  concurrency group and do not cancel a run during publication.
- For ordinary prose items, document one unambiguous `## Closure evidence`
  section containing observed results and limits. Pass its content verbatim as
  retirement evidence, without summarizing or truncating it. Missing, empty, or
  ambiguous sections cause a reported skip. Do not interpret an Exit conditions
  section as proof that those conditions were observed.
- For devloop items, reference recorded evidence identities and results rather
  than rerunning gates or judging historical completion against today's expiry
  time. Preserve `recordSchema`, `schema`, `bodyProfile`, `helper`,
  `requirementsDigest`, and `admission` in the retained consumer entry, using
  the pinned consumer contract and existing adapter. The full body, epoch, and
  evidence remain in exact MyQue history. Report and skip missing required
  records, unsupported versions, and unknown consumer namespaces; do not silently
  discard consumer data or infer evidence.
- Run `just tasks_check` before and after retirement. The pre-retirement check
  must validate live spec-driven bodies, which the terminal-only check cannot
  validate. Invoke MyQue for every canonical storage mutation; do not synthesize
  terminal records or a second persistent queue or manifest.
- Verify exact retained bytes and limit the resulting diff to deletion of each
  selected Markdown file and addition of its same-UUID terminal record. Preserve
  envelope version, UUID, title, lifecycle timestamps, state, and relationships.
- Push and verify this batch's retained refs before publishing the maintenance
  branch or PR. A failed history push prevents PR publication. Never remove
  retained history automatically to undo a partial publication.
- Keep at most one open retirement PR. An existing one stops a new batch rather
  than rewriting a branch under review. After an interrupted publication,
  inspect and verify an existing bot branch or PR before resuming; do not
  overwrite unexpected commits or create duplicate PRs.
- Include source revision, UUIDs, titles, evidence sources, retained commits,
  verification, and skip reasons in the PR or linked run report. Require normal
  CI and human merge; do not write directly to `main` or enable automatic merge.
- Protect against a candidate being edited or reopened on `main` while its PR
  is pending. Verify repository merge rules require current-base checks, or
  establish an equivalent enforced freshness boundary before enabling scheduled
  publication. Workflow concurrency alone does not protect against branch edits.
- Use `GITHUB_TOKEN` with only required contents and pull-request write access.
  Account for approval requirements on CI triggered by token-created PRs; do not
  claim unattended CI without observing it. Keep privileged PR events and item
  content out of the executable control path. Leave the existing projection
  workflow's canonical-store read boundary unchanged.

## Non-goals

- Closing items, proving past completion, synthesizing observations, or bypassing
  devloop completion. Direct `myque close` can bypass devloop eligibility, so a
  done state alone does not prove that `devloop complete` was used.
- Bulk v1-to-v2 migration, cancelled-item retirement, or backfilling historical
  closure evidence to make old prose automatically eligible.
- Shrinking Git history, pruning retained refs, automatic merge, or adding a
  personal access token or GitHub App as a prerequisite.
- Replacing MyQue storage or devloop semantics, adding a new schema authority,
  or using the GitHub projection as canonical state.

## Expected implementation surface

- `.github/workflows/myque-retire.yml`: triggering, permissions, isolation,
  concurrency, remote history publication, branch creation, and PR publication.
- `scripts/lib/work_item_retirement.py`: preview/apply entry points, candidate
  and evidence policy, MyQue invocation, and exact-result verification.
- `scripts/lib/devloop.py`: consumer retention handling through the existing
  adapter rather than a parallel consumer implementation.
- `scripts/check/check-work-items.py`: extend the existing control mechanism for
  retirement policy and failure cases; no new top-level checker is needed.
- `docs/getting-started/06-work-item-lifecycle.md` and `CONTRIBUTING.md`: closure
  evidence, automated maintenance PRs, retained-ref transport, and recovery.

Reuse existing pinned tool environments where suitable. Any additional build
configuration must be justified by the actual execution requirements, not by
introducing another copy of the toolchain pins.

## Exit conditions

1. In disposable stores, done v1 and v2 items retire without migration; open,
   active, blocked, deferred, cancelled, and already retired items are unchanged.
   Preview changes neither the canonical store nor remote refs, branches, or PRs.
2. Empty runs and retries do not create duplicate branches or PRs. An existing
   open retirement PR is not rewritten. Interrupted publication resumes only
   after verifying that existing remote state is the expected bot-owned result.
3. Missing or ambiguous prose evidence, missing devloop retention information,
   unknown consumer namespaces, and unsupported versions are reported without
   retiring those items or fabricating evidence. Corrupt stores fail before
   publication rather than being treated as eligible input.
4. Before/after checks pass; UUID resolution, dependency readiness, state,
   timestamps, and relationships are unchanged. Full item bytes and consumer
   entries are verified in retained snapshots, and reopening in a disposable
   repository restores the same UUID and original body.
5. A local bare-remote experiment demonstrates retained-ref push failure blocks
   branch/PR publication, partial publication can be retried safely, and a fresh
   clone with explicitly fetched retained refs can recover retired content.
6. A candidate edited or reopened on `main` cannot be retired by merging stale
   results. Observe the required merge/check behavior, including the race after
   planning; a local pre-push comparison alone is insufficient.
7. Observe a real GitHub manual run, maintenance PR, restricted diff, retained
   refs, and the actual CI triggering/approval path before enabling the daily
   schedule. Confirm no direct `main` write or automatic merge is possible
   through this workflow's supported path. Record the tested revisions and
   remote identities; local simulations do not satisfy this obligation.
8. Run the applicable `just tasks_check`, `just docs_check`, `just ruff`, and
   `just typos` checks, plus workflow syntax validation. Record actual results
   and limits in this item's closure evidence, not merely implementation status.

## Delivery boundary
