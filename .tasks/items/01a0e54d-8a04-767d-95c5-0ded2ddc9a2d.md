# Manager and probes adopt boot-store v1, qualified by one plane that stages through the manager and selects through the selector

## Context

Deferred by `docs/decisions/bootstate-partition-layouts.md`, which closed `01a0e395-3d12-7a17-b6ed-9aac687f635f`. Boot-store v1 (`contracts/bootstate/v1`: BootState at partition-relative LBA 0-1, directory at byte 4096, releases from 8192, generations from 16384) is the only product layout, and `slime-root/src/boot_selector.rs` reads it. `components/services/sel4-generation-manager` and the rollback, recovery, and transfer probes instead keep BootState at LBA 1024-1025 inside an object-store partition (`contracts/store/disk/v1`, whose superblocks occupy LBA 0-1), built by `scripts/build/build-store-fixture.py`, and the manager recognizes two constant identities rather than a directory of signed generations.

## Scope

- The manager reads and commits BootState in boot-store v1, and stages only a generation whose bytes and detached release are present in the boot-store directory.
- The rollback, recovery, and transfer probes and their fixtures move to the same layout, or state why a probe keeps a fixture-only layout.
- The fixture-only LBA 1024/1025 regions are removed once nothing reads them.

## Exit condition

Observed, not documented: one QEMU plane stages a signed candidate through the manager, reboots the same disk into a selector image, and observes the selector select that candidate, consume an attempt, and promote or roll it back. The decision record is then marked superseded and `docs/architecture/generation-management.md` stops listing two layouts.

Deferred because this is production-generation work, not a backlog repair; revisit when a component must write a generation a root will select.
