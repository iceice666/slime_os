# Retire history-only aliases and migration scaffolding

## Problem

`just/compatibility.just` and the documentation workflow preserve command names,
templates, chronological-index obligations, and migration helpers that may be
needed only by records moved to history. Deleting them before the archive
cutover would break current consumers or erase fail-closed qualification
semantics; retaining all of them forever keeps history coupled to the product.

## Scope

- Start only after H3 is merged. Inventory every recipe in
  `just/compatibility.just`, its canonical target, source-tree consumers, CI and
  supported-documentation consumers, qualification meaning, and uncertainty
  about external users.
- Delete an alias only when its remaining purpose is demonstrably historical.
  If an active consumer exists, migrate it in the same change to a semantically
  equivalent canonical recipe or retain the alias. Absence from source search
  does not prove absence of external use; uncertain public commands remain with
  a precise compatibility note.
- Treat `storage_nvme_read_check`, `framework_inventory_check`, and any similar
  unavailable qualification as fail-closed product requirements, not aliases.
  Preserve their rejection behavior or move them without semantic change.
- Add a focused control that detects removal of a recipe with an active docs,
  task, script, or CI consumer. Do not infer historical equivalence merely
  because two current commands delegate to the same target.
- Remove the obsolete devlog template, live chronological-index maintenance
  rules, compatibility comments that refer only to archived records, and
  one-shot migration scaffolding left after H3.
- Any retained transition command must perform a meaningful check; no empty or
  unconditional-pass shell remains.

## Exit conditions

1. Each compatibility recipe has a recorded disposition: retain, migrate active
   consumers then delete, historical-only delete, or fail-closed qualification
   preserve/relocate.
2. Product documentation, tasks, scripts, CI, and supported commands contain no
   reference to a deleted recipe; a negative control proves such a reference is
   detected.
3. Every remaining qualification and refusal recipe keeps its observable
   behavior, including missing-evidence and unsupported-path failures.
4. Current command aliases exist for current compatibility only, not solely to
   satisfy archived prose.
5. No devlog template, chronological index, obsolete migration helper, or
   silent no-op checker remains in the product repository.
6. General development still requires no history checkout or network access.

## Non-goals

Do not remove an uncertain public command, reinterpret an old gate's scope,
weaken fail-closed hardware/storage checks, or clean unrelated Justfile names.

## Verification

Run focused recipe-consumer controls, current documentation and task checks,
`just typos`, `just ruff` if Python changes, strict Justfile/CI parsing, and the
affected canonical aggregates or representative gates. Explicitly exercise
every preserved fail-closed recipe changed by the implementation.
