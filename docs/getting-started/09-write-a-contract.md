# Write a contract

[Contracts](../concepts/contracts.md) says why every boundary-crossing format
is a Zutai schema. This page is the mechanics: the files a new protocol or
record touches, the generator that turns the schema into Rust, the check that
refuses drift, and where the validator and the test live.

Do this before writing any Rust that packs bytes. A `#[repr(C)]` wire struct,
a hand-written offset, or a `struct.pack` layout in a checker is the mistake
this page exists to prevent; `just contracts_check` and review will both
refuse it.

## The shape of one contract

```
contracts/<name>/v1/
├── schema.zt      # the source of truth: constants, record types, packed layouts
└── gen_rust.zt    # pure renderer: schema → Rust (and C / Python where consumed)
```

Every contract has a version directory. A superseded version keeps its
directory as decodable history (`contracts/generation/v2..v4`,
`contracts/component/v1`) and is type-checked by `contracts_check` so it
cannot rot; nothing generates from it.

Two families exist, distinguished by who consumes the bindings:

| Family | Consumer | Generator | Output |
| --- | --- | --- | --- |
| **Boot and persistence** — generation, kernel image, target profile, BootState, release, budgets, authorities | `boot-contracts` (decoded by the root at admission) | one script for all of them: `scripts/generate/generate-boot-bindings.py` (`just boot_gen`), whose `GENERATORS` table lists each schema | `boot-contracts/src/generated/<name>.rs` and `scripts/lib/boot_contracts.py` |
| **IPC and service protocols** — spawn, block, store, fs, io-queue, network, powerbox, generation-management… | `components/proto` (`slime-proto`), used by components on both sides | one script per protocol: `scripts/generate/generate-<name>-bindings.py` (`just <name>_gen`) | `components/proto/src/<name>.rs`, sometimes `components/runtime/include/slime/<name>.h` |

Pick the family by consumer. If the root decodes it while admitting a
generation, it is boot family; if two components exchange it at runtime, it
is a protocol.

## Anatomy of `schema.zt`

[`contracts/spawn/v1/schema.zt`](../../contracts/spawn/v1/schema.zt) is a
good template for a fixed-size request/reply protocol. Its parts, in order:

1. **A header comment** stating what the format is, its size discipline
   ("fixed 64-byte IPC messages"), and how capabilities travel. This is the
   contract's documentation; the generated file points back to it.
2. **Constants** — `formatVersion`, lengths, maxima, flag and role bits:

   ```
   formatVersion :: Int = 1;
   requestLen :: Int = 64;
   maxCommandBytes :: Int = 16;
   requestFlagWait :: Int = 1;
   ```

   Every bound a validator will check is declared here, once.
3. **Record types** — logical fields:

   ```
   SpawnRequest :: type {
     magic : Int; version : Int; flags : Int; command_len : Int;
     ...
   };
   requestSchema ::= schema SpawnRequest;
   ```
4. **Packed layouts** — the concrete little-endian wire form, one entry per
   field, in field order:

   ```
   requestLayout :: List WireField = {
     { name = "magic"; width = 4; signed = false; byteArray = false; };
     { name = "command"; width = 16; signed = false; byteArray = true; };
     ...
   };
   ```

   The renderer checks that the layout names match the record's fields in
   order and that widths sum to the declared length, so a field added to the
   type without a layout entry — or vice versa — fails generation rather than
   silently shifting offsets.
5. **A `format` record** bundling constants, reflected fields, and layouts,
   and a `main` that calls `gen.render format` and writes the outputs under
   an environment-supplied root:

   ```
   main :: { write : FsWrite; env : Env; } -> Unit ! { ... }
     = caps => [
       root := env.get caps.env "SLIME_SPAWN_BINDINGS_ROOT" ?? ".";
       bindings := gen.render format;
       fs.writeAll caps.write (t.join "" { root; "/components/proto/src/spawn.rs"; }) bindings.rust
     ];
   ```

`gen_rust.zt` is a pure function from that `format` to text; it imports
Zutai's `wire.rust` / `wire.codec` helpers, so a new fixed-layout protocol
usually copies an existing renderer and renames the types. Do not put
policy in the renderer.

## The generated Rust

What comes out (`components/proto/src/spawn.rs`) is marked
`// @generated by contracts/spawn/v1/gen_rust.zt; do not edit.` and contains:

- one `pub const` per schema constant (`FORMAT_VERSION`, `REQUEST_LEN`,
  `MAX_COMMAND_BYTES`, `REQUEST_FLAG_WAIT`…), plus a `<NAME>_MAGIC`;
- one `pub struct Wire<Record>` per record with plain field types
  (`u32`, `u8`, `[u8; 16]`);
- `decode(&[u8]) -> Option<Self>` and `encode(self) -> [u8; LEN]` that
  implement exactly the layout.

Nothing in it validates semantics. Magic and version checks, bound checks,
and flag combinations live in a hand-written validator beside the generated
module: `components/proto/src/lib.rs` has `valid_spawn_request`,
`valid_block_v2_request`, and so on. That validator is where "flags may be
`WAIT` or `SHUTDOWN` but not both" is written once and used by both the
client and the service.

## The steps

Adding a protocol `widget` for two components:

1. **Author** `contracts/widget/v1/schema.zt` and `gen_rust.zt`, copying the
   nearest existing pair. Choose the output path(s) in `main`.
2. **Add the generator** `scripts/generate/generate-widget-bindings.py` by
   copying `generate-spawn-bindings.py`: it stages the render into a temp
   directory, compares with the committed output, and supports `--check`.
   Add a recipe in `just/generate.just`:

   ```just
   [group('generate')]
   widget_gen:
       python3 scripts/generate/generate-widget-bindings.py
   ```
3. **Generate and commit** both the schema and the output:

   ```sh
   just <name>_gen        # widget_gen in this example
   ```
4. **Register the drift check.** Add the `run("check", …)` lines for the
   schema and renderer plus the `--check` invocation of your generator to
   `scripts/check/check-contracts.py` (the protocol family) — or add the
   schema to `GENERATORS` in `generate-boot-bindings.py` if it is boot
   family, which `boot_gen --check` then covers. Contracts that
   `contracts_source_check` lists directly in `just/contracts.just` follow
   the same pattern. From now on a schema edit without regeneration fails
   `just contracts_check`.
5. **Write the validator** in `components/proto/src/lib.rs`
   (`valid_widget_request`) and `pub mod widget;`.
6. **Test it** in `components/proto/tests/widget.rs`: encode/decode round
   trip at the exact length, every bound at its edge, every refused flag
   combination. `just test_host` runs it, and `just miri_proto` checks the
   decoder for undefined behavior.
7. **Use it** from both components through `slime_proto::widget::*`. If the
   protocol is carried on a native endpoint, its 64-byte fixed size is not a
   coincidence: `MAX_MESSAGE_BYTES = 64` is the root's payload bound
   ([capability matrix](../capability-matrix.md), "Bounds"). Larger records
   travel through a shared buffer or the transfer window.
8. **Document** it: a `contracts/widget/README.md` when the protocol has
   authority semantics worth a page (`network-service`, `system-spec` do),
   otherwise the schema's header comment is the documentation. Add the
   contract to the owning `docs/architecture/` page's ownership table.
9. **Regenerate the closures** — `contracts/` trees are part of every
   system-image closure, so `python3 scripts/generate/generate-system-image-closures.py`
   before any plane gate.

## Versioning

- A compatible addition (a new flag bit, a new constant) stays in `v1`.
- A layout change is a new version directory. Keep `v1` in place and
  type-checked; superseded generation formats are refused at decode, never
  migrated, and that refusal is what makes a bump rollback-safe.
- The version travels in the record (`version` field, `FORMAT_VERSION`) and
  the validator checks it; a decoder never guesses from length.

## What is exempt

Readers and writers of formats Slime OS does not own — ELF, GPT, Ethernet/IP,
MAVLink, SSH signatures — may use the standard's offsets directly. Purely
in-memory types need no schema. Everything else that is persisted, sent
between processes, or handed to the boot path is a contract.
