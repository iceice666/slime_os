# Raspberry Pi 5 ROS 2 demo contract format 1

This directory defines RP0's target-qualified acceptance contract for the first Raspberry Pi 5 ROS 2 two-node demo. `schema.zt` is the normative cross-boundary shape. `fixtures/valid.zti` freezes the exact board, firmware, media, serial path, ROS/DDS profile, two-node workload, bounds, capabilities, evidence trace, and operator markers that later milestones must implement.

Format 1 selects:

- Raspberry Pi 5 Model B revision 1.0 boards with official revision codes `c04170` or `d04170`;
- the Raspberry Pi 5 EEPROM boot flow from removable microSD, using `kernel8.img`, `config.txt`, and `bcm2712-rpi-5-b.dtb`;
- the firmware-final device tree as the memory-map/device source, the device-tree-described Arm GIC-400 and Armv8 generic timer, and UART10 on the dedicated debug header at 115200 baud;
- ROS 2 Jazzy semantics implemented as Slime-native ROS-compatible components through a bounded Slime RMW/DDS Profile 0, not unmodified upstream packages and not a DDS-free local shortcut;
- DDSI-RTPS 2.5, little-endian XCDR1 plain CDR, static generation-declared discovery, two fixed participants, one reliable volatile writer/reader pair, exact loopback locators, and bounded DATA/HEARTBEAT/ACKNACK behavior;
- a four-sample `slime_demo_msgs/msg/Counter` workload with exact subscriber values and sequence order;
- a dedicated versioned semantic/DDS trace whose required success sequence reaches the success marker only after all samples are decoded and validated and reliable teardown completes.

## Validation levels

Zutai decoding validates the closed record shape. `scripts/check/check-rpi5-ros2-demo-contract.py` owns semantic admission:

- `formatVersion`, contract id, target, board, revision set, firmware, ROS profile, and DDS profile are exact closed values;
- every count, string, payload, RTPS record, fragment, queue, history, retry, trace, log, and capability list is bounded before activation;
- participant, endpoint, locator, workload, type identity, QoS, sequence, teardown, and success-trace values are internally consistent;
- the capability inventory covers both nodes, the DDS runtime, board services, removable storage, exact datagram destinations, clocks, logs, and the trace sink without wildcard or ambient authority;
- success/failure markers are exact and distinct for denial, timeout, wrong board, wrong target, malformed RTPS, malformed XCDR, and malformed generation;
- unknown board, firmware, ROS/DDS profile, and target identifiers are rejected independently by one-delta negative fixtures generated by the check.

No format-1 reader may select a nearby target, firmware, or profile. Unknown required values require a new contract version or a separately admitted exact profile.

## Scope boundary

RP0 fixes the demo contract; it does not claim that the kernel, DDS runtime, AArch64 QEMU path, or physical board path exists yet. RP1-RP8 and R0 implement and observe those claims. DDS Security, dynamic LAN discovery, multicast, wildcard destinations, services/actions, arbitrary ROS packages, Python, filesystems, parameters, Wi-Fi, GPU, and internal-storage writes are outside Profile 0.

Run the focused gate with:

```sh
just rpi5_ros2_demo_contract_check
```
